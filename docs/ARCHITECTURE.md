# Architecture

This document maps what Nebulosa already has, where each feature belongs, and the contracts new features must follow. It is the reference for the next deliveries, in this order: Tools, Sky Framing, the remaining camera operations of Images, then Sequencer. Repository rules (boundaries, style, verification) live in [`AGENTS.md`](../AGENTS.md).

Reading order for a new contributor: the Glossary and the Architecture Map, then Adding a Feature, then the Workspace Responsibility Matrix and UI and Layout Contracts for anything visible, then the contract of each feature the change touches.

## Glossary

- **Connection**: an open INDI, Alpaca, or simulator client on the server (`api/src/connection.ts`), identified by its connection id. Saved connections (host, port, type) are browser data; open ones are server state shared by every tab.
- **Device**: one interface a connection reports (camera, mount, focuser, …), identified by connection id + device id (`DeviceSummary`). Several interfaces of one physical device share a hardware id.
- **Profile**: the browser-side workspace of an operator (`web/src/profile/`): its saved connection, equipment setup, optical presets, and preferences. Profiles never reach the server.
- **Equipment setup** and **role**: the assignment, in a profile, of devices of its connection to operational roles (`EquipmentRole` in `web/src/equipment/roles.ts`: `MAIN_CAMERA`, `GUIDE_CAMERA`, `MOUNT`, `FOCUSER`, `FILTER_WHEEL`, `ROTATOR`, `GUIDE_OUTPUT`, `DOME`, `COVER`, `FLAT_PANEL`), edited in the Equipment Setup modal, which connects or disconnects the assigned devices one by one or all at once (Connect all, Disconnect all: `switchSetup`). Roles only choose devices in the UI; every command still names the exact device.
- **Operation**: a server-owned piece of device work holding devices under the `OperationRegistry` (`OperationKind` in `api/src/operations.ts`), observed through `operation:updated`.
- **Session**: the record of a multi-step operation of one service (a capture, an Auto Focus run, a held mount nudge or dome rotation), with its own events.
- **Image document**: decoded pixels in the server's `ImageStore`, addressed by an image id; files, camera frames, and derived images are all documents.
- **Camera tab**: the permanent tab of Images for one connected camera, showing its frames and hosting its camera operations.
- **Lease**: a hold a client keeps on a server resource (a capture frame's document, a held motion) that the server releases when the client goes away.

## Architecture Map

| Layer   | Owns                                                                                                                                            | Never owns                                        |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `core/` | Algorithms and device protocols: INDI/Alpaca clients, commanders, orchestration, capture runner, solvers, star detection, ephemerides, eclipses | Application state, HTTP, UI                       |
| `api/`  | Runtime services: connections, devices, operations, image documents, sky queries; HTTP routes and the event WebSocket                           | Presentation state, profiles                      |
| `web/`  | Presentation: workspaces, profiles, selection, view state; mirrors of server state fed by HTTP and events                                       | Operations, device arbitration, scientific pixels |
| `app/`  | Wiring `api` and `web` into one `Bun.serve` and the build                                                                                       | Business logic                                    |

Server state reaches every tab through `GET` snapshots plus the `/api/ws` event stream (`ServerEvent` in `api/src/websocket.ts`). A tab refreshes its snapshots on every socket open (`onOpen` in `web/src/main.tsx`), so a reload never loses running work. Each web store that mirrors server state is listed once in `SERVER_STORES` (`web/src/main.tsx`) with its event handler and its refresh. Events keep arriving while a snapshot is fetched, so an event may be applied before the response of an older snapshot: the operations and captures stores record, through `SnapshotRefreshes` (`web/src/refresh.ts`), the operations and cameras their events change during a refresh, and the snapshot leaves those as the events set them.

One stream is the exception: the INDI property stream of a physical device (`api/src/indi.ts`, see INDI Properties Contract) is never broadcast. A tab asks for it with an `indi:subscribe` message over its own `/api/ws` socket (`ClientMessage`, the only messages the server reads from a socket) and receives a full snapshot on that socket, then the changes, so snapshot and changes form one ordered stream without a `GET`; the subscription belongs to the socket, not to the tab's client id, and ends with it.

The control states of the devices of the active profile's connection are mirrored once in the web, by `controlRuntime` (`web/src/equipment-control/control.ts`), from `GET /api/connections/:id/states` and the `<type>:updated` events. A view that follows one device, such as the Sky mount (`mountView`), Mount Nudge, the camera capabilities of Camera Acquisition and Auto Focus, or the sensor geometry of the Equipment Setup field of view (`CameraCapabilities.sensor`, `liveSensors`), reads that mirror (`watchedDeviceState`) and never fetches or tracks the device's state apart.

Each `api` service exposes its routes through a `create<Name>Routes(service)` factory in its own module; `api/src/index.ts` only composes the services, spreads their routes, and serves `/api/health` and `/api/ws`. One route is composed by `app/src/main.ts` instead: `createAboutRoutes` (`api/src/about.ts`) serves the identity of the distribution, which `app` owns (its package version, and the commits and compile time `app/build.ts` inlines into the executable), so `api` never imports `app`.

Every error response of `api` is `{ error, code }` (`ApiError` and `errorResponse` in `api/src/http.ts`): a message meant for people and a stable code a client branches on, never the message. Each service names its codes (`CommandErrorCode`, `StarDetectionErrorCode`, `PlateSolveErrorCode`, `CaptureFrameErrorCode`, and the codes its routes document), and a route may add documented fields, such as the current state after a `conflict`.

The types the web shares with the server are exported by `api/src/index.ts` and imported with `import type { … } from 'api'`; a new payload or event type is exported there.

## Adding a Feature

The path every new capability follows, so it lands in one place and is observable from every tab:

1. **Toolkit first.** If the algorithm or protocol is missing, it belongs to `nebulosa.ts` (`core/`), not to this repository.
2. **Server service.** A class in its own `api/src/<name>.ts` taking its collaborators in the constructor (devices, client lookup, `OperationRegistry`, `ImageStore`, `ExternalToolsStore`, `broadcast`), with a `create<Name>Routes(service)` factory beside it, composed in `api/src/index.ts`. Device work runs as an operation; image analyses use the shared `AnalysisScheduler`; settings that belong to the server instance are versioned files under `~/Nebulosa/`.
3. **Contract.** Payload, state, and event types exported from `api/src/index.ts`; error codes named; the event added to `ServerEvent`.
4. **Web mirror.** A `valtio` store fed by a `GET` snapshot and the event, registered once in `SERVER_STORES` (`web/src/main.tsx`), with pure, injectable-`fetch` tests. Device state is read from `controlRuntime`, never fetched apart.
5. **One place in the UI.** An entry in the registry of its workspace (`IMAGE_TOOL_DEFINITIONS`, `TOOL_DEFINITIONS`, the Sky panel views, `CONTROLS`, or a new `WORKSPACE_IDS` entry), following UI and Layout Contracts. A registry entry may exist before its view only as planned.
6. **Preferences.** Per-operator form values go into the profile (a new `PROFILES_VERSION` and `migrate` case when the shape changes); per-device forms are keyed by the physical device, never by a role.
7. **This document.** The inventory row, the matrix rows, and the feature's contract section are updated in the same commit.

Connections, Equipment Setup, and profiles are modals of the shell (`ConnectionModal`, `EquipmentModal`, `ProfileModal`), not routes. ## Shared Image Contracts

There is **one** image store, `ImageStore` in `api/src/images.ts`, and the scientific image reference is its document id.

- An image document is addressed as `/api/images/:id/...` by every operation, whatever workspace requested it. There is no second solver or detector path for camera frames.
- Camera frames enter the store as documents of the origin `{ origin: 'capture', connectionId, deviceId, frameId, time, path? }` (`ImageStore.openCapture`), decoded from the bytes the driver sent. A frame is never identified by camera role.
- In loop capture, each frame is its own document. An analysis stays bound to the id it was started on, and a newer frame never changes it. The capture frame registry (`api/src/captureframes.ts`) keeps the latest frame of each camera open and closes the previous one unless a lease of the Images workspace holds it (see Capture Frames Contract). An analysis retains its document (`ImageStore.retain`/`release`): closing it hides it from every route at once, but its pixels are released only when the last analysis lets it go.
- A derived document is computed from another document and never changes it. Its provenance (`processing`) records the steps of the image processing pipeline that computed it (see Image Processing Contract), whose result the store adopts (`ImageStore.adopt`) from a full copy it handed out (`ImageStore.processingImage`). It is floating point, keeps the min-max rescale of the source read so a save writes the scale of the source, and records its source, time, and what was applied in HISTORY.
- Analysis results (solution, star list, streaks) are keyed by image id and the parameters applied, and are kept in memory with the document until its pixels are released. Re-running with the same parameters reuses the result. The web stores of star detection, streak detection, plate solving, and annotation mirror their jobs through `trackJob` of `web/src/analysis.ts`: the latest job of each image, a bounded set of fetched results, and a job state that only moves forward, so a snapshot or a submission answer arriving after the events of a job never takes an ended job back.
- A Sky Framing survey image is not an image document. Importing one into Images is an explicit action, available only when the cutout carries usable WCS metadata.

## Capture Frames Contract

- `CaptureFrameRegistry` (`api/src/captureframes.ts`) indexes the frames of Camera Capture, Auto Focus, TPPA, DARV, Flat Wizard, and Guiding by physical camera (connection id + device id, never a role, profile, tool, or operation). A frame is identified by its `frameId` (`sessionId:generation`, the capture, Auto Focus, TPPA, DARV, Flat Wizard, or guiding session and the frame number within it), the acquisition, and its `origin` (`capture`, `autofocus`, `tppa`, `darv`, `flatWizard`, or `guiding`) names the operation that took it; its `imageId` is only the document currently holding its pixels, and a saved frame reopened from its file gets a new one. Frames are ordered by a registry-wide `sequence`, never by time, and every change carries a `revision` so a late event never replaces a newer state. Both producers share one latest frame per camera, ordered by the order the registry received them, never by their session numbering, and a write completing late never takes the latest frame back. Auto Focus records every sampled and verification frame it decoded, before it is measured and whether or not an HFD could be measured; its files are auxiliary and deleted, so its frames are never saved, and only become the latest frame and then transient frames. TPPA records its poses and refinement frames the same way, before they are solved, and DARV the frame of each measurement, before it is analyzed. Guiding records only the newest guide frame it previewed, which is never saved. Flat Wizard records every trial and final frame from its staging file before it is measured; an accepted frame becomes saved through `published()`, the only change of a frame's path, which names the final file it was published under (a frame the registry does not know is recorded from that file), while trial and rejected frames stay previewed only and become transient. `written()` only records the outcome of a write to the path a frame already names.
- Each camera keeps two collections with separate retention: its **latest** frame, the newest one the preview decoded since the server started (previewed only, being saved, or saved), and its **saved** frames, the newest `FRAMES_PER_SOURCE` (20) frames whose file was written, the only history. A frame joins the saved frames only once its write succeeds (a failed write never does), so any number of previewed-only frames never evicts a saved one, and a previewed-only latest frame takes no saved slot; a saved latest frame is also the newest saved frame. A former latest frame that was not saved is kept in memory as a **transient** frame (at most 20 per camera), never listed nor persisted, only so its state can still be asked for.
- The registry never holds pixels. A frame is `memory` while its document is open, `file` when its saved file exists (opened as a new `file` document on demand), `saving` while its file is written and its document closed, or `unavailable` (`expired`, `fileMissing`, `saveFailed`, `restarted`). A saved frame the preview skipped is recorded from its file; a skipped frame that was only previewed is not. Opening never substitutes another frame.
- The registry owns the closing of capture documents, Auto Focus frames included: the latest previewed frame of each camera stays open, an older one only while a lease holds it. `POST /api/capture-frames/frames/:frameId/open` leases the document for a client (the id a page opens `/api/ws?client=<id>` with, `clientId` of `web/src/events.ts`, generated on load since Images documents do not survive a reload); `DELETE /api/capture-frames/leases/:lease` releases it. At most `MAX_LEASED_FRAMES` (16) documents are kept open by leases besides the latest frames; beyond that an open is refused with `limit`. Refusals carry the codes `notFound`, `expired`, `fileMissing`, `saveFailed`, `saving`, `limit`, and `unreadable`.
- When the last socket of a client closes, its leases are released after `LEASE_GRACE` (10 min), so a phone whose screen locked finds its frames again; a tab that reopens its socket sends the leases it still uses to `PUT /api/capture-frames/clients/:client/leases`, which releases the others and answers the lost ones; a page that unloads releases all of its leases with a beacon (`POST` on the same route).
- `GET /api/capture-frames` is the snapshot of the cameras (with an `epoch` per server run): each camera gives its `latestFrameId`, its `latestAvailableFrameId` (the latest frame, or the newest saved frame whose file exists when the latest cannot be opened or there is none), `latestRestored` (no latest frame since the server started), and `count` of saved frames. `GET /api/capture-frames/sources/:connectionId/:deviceId` gives the `latest` frame and the saved `frames`, newest first (a page with a reserved `next` cursor; empty for a camera without frames), and `GET /api/capture-frames/frames/:frameId` one frame (latest, saved, or transient). Changes are published as `captureFrame:updated` (frame and camera) and `captureSource:updated` (connection state); neither carries pixels or server paths, only file names. A disconnected camera keeps its frames.
- The saved frames of at most `MAX_SOURCES` (32) cameras are persisted in `~/Nebulosa/capture-frames.json` (version 3, `saved` per camera with each frame's `origin`, written atomically at most 2 s after a change). A frame of a version 1 or 2 file, or with an origin that is never saved, is read as a `capture`. A version 1 file, whose `frames` mixed previewed-only and saved frames under one limit of 20, is read keeping its saved (and being-saved) frames only; saved frames it had already evicted cannot be recovered. After a restart no frame is in memory and no camera has a latest frame: saved frames are available when their file still exists, and previewed-only ones are gone. No directory is scanned.
- Images has a permanent **camera tab** for each connected camera of the profile's watched connection (`deviceState` of `web/src/equipment/equipment.ts`, `reconcileCameraTabs` in `web/src/images/cameratabs.ts`), keyed by connection id + device id, ordered by camera name then id, before the closable file and derived tabs; cameras of the same name get the start of their id. It is created and removed with the camera, never closed by the operator (`isClosable`: no close button, middle click, or Delete), and switching profile or connection changes the camera tabs. A camera that disconnects loses its tab and lease; its zoom, pan, display settings, and tool are kept in memory and given back when it reconnects.
- A camera tab shows one frame at a time by its selection: `latest`, the camera's latest available frame (after a restart, the newest saved frame, labelled Latest saved), followed as each newer frame in memory arrives, only the newest of those arriving while one opens being shown; `saved`, a saved frame, which new frames never replace; or `inspect`, the frame held when Run Detection or Solve Image starts on a followed frame (`holdCameraFrame`), so the result stays on the frame analyzed. Return to Latest follows the camera again without replaying the frames in between. A selected frame that cannot be opened keeps the frame shown with the error and never falls back to another frame.
- Showing a frame is one transaction (`showCameraFrame` in `web/src/images/cameratabs.ts`): the frame is leased and rendered with the tab's applied display settings (before any, those its camera saved in the profile, or the frame's defaults; settings being applied meanwhile become the applied ones and are saved), plus its original rendering during Show Original, while the previous frame stays shown; then the frame, its document, and its renderings are committed together, zoom and pan are adapted to its size (`adaptView` in `web/src/viewer/transform.ts`: same size kept, a new size keeps the relative centre and the fraction shown, Fit stays Fit), the selected star and solution are cleared, and the previous lease is released. A frame asked for later supersedes one still opening, whose lease and renderings are released. Settings being edited in a popup of the viewer toolbar are never applied by a frame change. Overlays and results follow the image id of the frame shown, and the Image Inspector shows its camera, connection, origin (Camera Acquisition or Auto Focus), frame, storage state, and why it is shown, and for an Auto Focus frame its session, measurement or verification, and the focuser position its session recorded (`autoFocusFrameFocus`; nothing when not recorded yet). A frame without a known star detection fetches the jobs kept for its image (`GET /api/images/:id/stars`), so the measurements of Auto Focus are shown without a new detection.
- Below the viewer of a camera tab, the capture frames carousel (`web/src/images/CaptureFramesCarousel.tsx`) shows the Latest card first (the latest available frame, Latest saved after a restart, marked New while another card is selected and a newer frame exists), then the saved frames newest first, without the frame Latest already shows. Cards show metadata only (number, time, exposure, a floppy disk icon once the frame's file is written, the Latest card included, a state only while loading, failed, or missing, and a tooltip with id, size, file, and availability; the selected card is marked by its outline alone) and an icon in the area reserved for a future thumbnail; no pixels are loaded for them, and the saved frames of a camera are fetched when its tab is shown. A saved frame that cannot be opened shows why and cannot be selected. Arrow keys, Home, and End move between cards, Enter or Space selects one; selecting a card only opens and renders its frame, never an analysis. The toolbar hides and shows the carousel without changing the selection.
- On every socket open the snapshot is fetched first (a camera an event of the same server run made newer is kept), then the leases of the camera tabs are reconciled and each tab shows its selection again: a lost lease reopens the same saved or held frame from its file, or the latest one; without a frame to show, the tab keeps its pixels and says the frame is no longer available.
- Limitations: a previewed-only frame can be opened only while it is the latest of its camera or leased; a tab asleep for longer than the grace period may lose such frames; analysis results are keyed by image id, so a frame reopened from its file shows none of the results of its first document; the records of the last 2 s may be lost in a crash, and a server stopped by a signal writes them first; Latest is the latest frame the preview decoded, and a loop may skip frames between two previews; only the cameras of the watched connection have tabs, so the frames of another connection's cameras are not shown; a disconnected camera has no tab, so its saved frames are reachable again only once it reconnects; the setup has no optical train, so the focuser and mount of a camera tab follow a fixed rule (the FOCUSER only for the MAIN_CAMERA, the MOUNT for every camera of the connection).

## Overlay Contracts

- Overlays draw through `ImageViewer`'s `overlays(size, view)` callback as SVG in **image pixel coordinates** (origin at the top-left of the first pixel). Zoom, pan, fit, 1:1, and resize are applied by the viewer, so overlays never compute screen coordinates; `view` gives the scale, for sizes constant on screen, and the visible region, to skip what is off screen. The viewer applies zoom and pan to the overlays as an SVG transform on a layer outside the CSS-transformed image, so strokes and dashes use `vectorEffect="non-scaling-stroke"` to keep their width on screen; a stroke inside a CSS transform would scale with it. Toolkit results use 0-based pixel indices with integer centres, so a result point (x, y) is drawn at (x + 0.5, y + 0.5).
- An overlay is a pure function of a result and the image shown: it draws only results whose image id matches the displayed image. Hiding an overlay never cancels or deletes the result, and showing one never re-runs the analysis.
- Celestial-coordinate overlays (annotation, grid) require a WCS solution of that same image: the one `usePlateSolution` selects (the chosen job or the header). Without one they are unavailable, not approximated. The WCS overlay (`web/src/platesolving/WcsOverlay.tsx`) draws the solved centre and north and east arrows from `web/src/platesolving/wcs.ts` (the toolkit's TAN/TAN-SIP transforms); the arrows and marker keep their screen size until they would exceed a quarter of the image's smaller side, then shrink with it. The RA/Dec grid (`WcsGridOverlay.tsx`, geometry in `grid.ts`) is shown per document independently of the centre: it covers the visible part of the image plus a 50 % margin, chooses its major step from a ladder of 1″ to 30° and 1s to 6h by the spacing of neighbouring lines measured across them on screen at five points (so rotation, SIP, and the convergence of meridians near a pole are followed), keeps a step while its spacing stays within 60–260 px, divides it into minor lines at least 18 px apart, traces each line with a subdivision bounded by a 0.5 px chord error (16 initial segments, depth 8, 256 segments), breaks it where the projection fails or jumps, and clips it to the region; at most 24 major lines per axis. The geometry is cached per solution while the view stays inside its region and within √2 of its zoom, so a pointer move never retraces it. Major lines are labelled where they cross the boundary of the visible image (declinations left then right, right ascensions bottom then top), horizontally at a constant 11 px, at most 48, dropping labels that would overlap on their side. Meridians and parallels are drawn in one theme color, or each in its own (reddish right ascension, bluish declination), lines and labels alike. The passive aids follow the same selected WCS without any request: the status line shows the right ascension, declination, frame, and local pixel scale under the pointer (`WcsCursorStatus`, one unprojection per move, "—" off the image or where the WCS fails); `WcsAidsOverlay` draws an optional crosshair, the compact north and east arrows 44 px inside the top-right corner of the visible image from the WCS at that point (an undefined arrow, at a pole, is left out; the orientation mode can draw them at the solved centre instead, or hide them), and the scale bar near the bottom-left corner: the longest round angle from 1″ to 5° spanning 60–180 px, its end found by bisection on the separation through the WCS where it is drawn, hidden when the two axis scales differ by more than 10 % there or it does not fit (`web/src/platesolving/aids.ts`). Coordinates are written in the profile's format and decimals (`coordinates.ts`), a display choice that claims no accuracy. Its `fitsToViewer` is the only place where a FITS pixel (1-based, integer centres) becomes a viewer point (minus half a pixel); the TPPA correction guide, whose geometry the server computes with the toolkit in that convention, converts through it too.
- `ImageViewer`'s `onImageClick(point, view)` reports a click (never a drag or a pinch) in image coordinates; the star markers use it to pick a star. The viewer stays unaware of what its consumers draw or measure; its other pointer contracts are generic and optional:
    - `overlays(size, view, cursor)` and `status(cursor)` receive the `ViewerCursor` (image point, zero-based pixel inside the image, viewport point), absent off the viewport, so the status line and overlays follow the pointer without re-rendering their owner.
    - `interaction` (`ViewerInteraction` of `web/src/viewer/interaction.ts`) lets a tool take presses: `onPointerDown` decides on the first pointer whether the tool owns the gesture, otherwise the viewer pans; hovers reach the tool too. The pure router `routeGesture` turns a second pointer into a pinch that cancels the tool (`onCancel`), as do `pointercancel` and a lost capture; nothing resumes until every pointer is lifted. A press of the pan released within the click tolerance is a click. Space held on the focused viewport pans whatever the tool; Escape cancels and Delete or Backspace deletes (`onDelete`) only while the viewport has the focus, so form controls keep their keys.
    - `crosshair` shows the crosshair pointer over the image whatever the interaction (Images sets it for every image with a solution, whose coordinates the status line always reads); Space held still shows the open hand of the pan.
    - `onImageContextMenu(point, client, view)` answers the native `contextmenu` event (a right click, or a long press on touch devices) and returns whether it handled it; otherwise the browser's own menu opens.
    - No screen-space layer exists: an overlay keeps a size constant on screen with `1 / view.scale` and places corner symbols from `view.visible`.
- An ROI is a region in image pixels. It never changes a camera's physical subframe unless an explicit, capability-checked command does it.

## World Map Contract

- `WorldMap` (`web/src/ui/WorldMap.tsx`) draws the basemap `web/assets/world.map.svg` (equirectangular, 2520.631 × 1260.315 map units, longitude −180° at x = 0 and latitude +90° at y = 0) with zoom (wheel, pinch, double click, `+`/`-`, buttons, from the whole map up to `MAX_WORLD_MAP_ZOOM` = 64×) and pan (drag, arrows), and reports a click, never a drag or a pinch, as a geographic position through `onSelect`; the owner keeps the selection and passes it back as `selected`, drawn as a marker. Geographic positions are degrees, longitude east positive. The owner moves the view through the `WorldMapHandle` ref (`centerOn`, `zoomBy`, `reset`).
- The map wraps across the antimeridian by default: the basemap and the children are drawn again one map width west and east, panning east or west never ends, and the smallest zoom fits the map's width. The graticule then draws the antimeridian once, at x = 0, as the seam between copies. With `wrap={false}` the whole map fits, the view is clamped to it, and the antimeridian is only its border.
- Children are SVG in map units, drawn over the basemap and the graticule: `geoPath` (unwrapped across ±180° by default, or split for a map that does not wrap) and `horizonRegionPath` (where a body is above or below the horizon, from its subpoint: the night side, the visibility of a lunar eclipse) in `web/src/ui/worldmap.geometry.ts` build their path data, and `WorldMapSymbol` places symbols of constant screen size. Toolkit eclipse paths fit when projected into the same map units; the API draws them on the degree plane (x = longitude + 180, y = 90 − latitude, in degrees), which `DEGREE_PLANE_TRANSFORM` scales to map units. Strokes use `vectorEffect="non-scaling-stroke"`.
- Zoom and pan never re-render React: the view is written to the layers once per animation frame. The basemap is a tile pyramid on a `<canvas>` (`web/src/ui/worldmap.tiles.ts`): level L is the whole map 2^L tiles of 256 device pixels across, up to level 11, rasterized from the SVG's shapes by a worker (`web/src/ui/worldmap.worker.ts`, started from a Blob of self-contained functions, so it needs OffscreenCanvas 2D in workers), so a frame only draws bitmaps already made and never waits for the thousands of country paths. A missing tile is drawn from the matching part of the nearest coarser cached tile and fades in when it arrives; levels 0 to 3 are fetched first and never evicted, so the map is never blank, and at most 256 tiles are kept. Borders keep the SVG's width up to 1.5 device pixels; the children are on an SVG layer with the same zoom and pan, which also sets `--world-map-scale` (viewport pixels per map unit). Children should be memoized by their owner, since the map renders them again whenever its own props change.

## Operation Lifecycle Rules

- Every device operation runs under the process-wide `OperationRegistry` (`api/src/operations.ts`). It owns a single `ResourceArbiter` and `OperationCoordinator`, plus a `DeviceLifecycle` that follows every managed device type.
- An operation holds its devices by physical identity (`resourceKey`). A second operation on a held device is refused as busy, whichever service or tab starts it. Disconnecting or removing a device cancels the operations holding it.
- Each start and end is published as `operation:updated` (`OperationRecord`: id, kind, exact devices, state, reason). `GET /api/operations` lists the running ones. The web mirrors them in `web/src/operations.ts`.
- Operations are owned by the server. Switching workspace, profile, camera tab, or mode, collapsing a panel, or unmounting a component never ends one.
- Interruptions are distinct commands, offered only when supported: cancel a pending request, abort an exposure, stop guiding, stop mount motion, stop a persistent service. There is no generic "Cancel".
- Long-lived services (guiding session, Mount Remote Control listeners, Alpaca server, sequencer run) are server objects with explicit start and stop and their own state events. They are not operations of a React screen.
- Existing protocols (PHD2 events, `CameraCapturer` reports) keep their own state machines. The registry tracks what they hold; it does not replace their states.
- The shared `CameraCapturer` of `api/src/captures.ts` (Camera Capture, Auto Focus, TPPA, DARV, Flat Wizard) allows `FRAME_TRANSFER_TIMEOUT` (10 min) for a frame's payload to arrive after its exposure, and for a stopped exposure to stop being Busy. INDI delivers in order, so a stop is answered only after the BLOB in transit, and an unbinned frame of a large sensor over a slow link takes minutes (an ASI294MM Pro frame of 124.8 MB in base64 took about 130 s at 1.2 MB/s). The camera stays held until then, and a frame that is really lost fails only after that time.

## Equipment Control Contract

- The page lists the devices of the active profile's connection only, grouped by hardware id, so the interfaces of one physical device (a flip-flat's cover and flat panel, a mount and its guide output) appear once. The INDI directory adds every device the connection reports that no interface manages, named in the URL by its hardware id. Opening it, switching devices, or reloading never connects, disconnects, or commands anything.
- Every command goes through `api` under the shared contract of `api/src/commands.ts`: settings answer 204 once applied, motions answer 202 with an operation id and report their outcome only through `operation:updated`. Durable requests carry a client token, so a repeated request never moves a device twice; the web generates tokens and ids with `nanoid`, never `crypto.randomUUID`, which browsers only provide in a secure context (HTTPS or localhost) and the app is usually opened over plain HTTP on the local network. Errors carry a stable `code`.
- Stops never wait for a lease: `POST …/stop` cancels the operation of the physical device and sends the commander's `stopMotion`. A filter wheel has no abort. Guide pulse stops never cancel another operation of the mount.
- Manual motion held by a lease (mount nudge, dome rotation) shares `api/src/leases.ts` and `web/src/press.ts`.
- Values shown are those the devices report; forms and sliders only hold pending values until an explicit action.
- The sensor temperature of a camera (`CCD_TEMPERATURE`) or a focuser (`FOCUS_TEMPERATURE`) is read by the toolkit's `ThermometerManager`, registered in `DeviceRegistry` after the managed types, and published in the parent's state (`temperature` of `camera:capabilities` and `focuser:updated`); its thermometer proxies are not a managed type. A camera reports a `cooler` only when it has a cooler switch or a settable target temperature, so a camera with a bare thermometer shows only its temperature.
- The mechanical type of a mount (`mountType`) comes from `TELESCOPE_MOUNT_TYPE` or the Alpaca `alignmentmode`, and is `UNKNOWN` until reported; only `ALTAZ` is evidence against a polar alignment, and the INDI base class reports `EQ_GEM` unless its driver says otherwise.
- Known driver differences: Alpaca mounts expose only Go Home (no find or set home, no set park, no flip); Alpaca domes cannot unpark or rotate manually; Alpaca focusers have no sync or reverse; Alpaca rotators have no home. Pier side and the INDI Alignment Subsystem are reported but have no commander, so the controls show them read-only; power, weather, safety monitor, and GPS devices are not managed. The vectors of all of them can still be seen and written in INDI Properties (see INDI Properties Contract). The simulator has no composite cover with a heater; that path is tested with a fake client.

## INDI Properties Contract

- The raw property vectors of every device of every connection, managed or not, are kept once in `DeviceRegistry.properties`, the toolkit's `IndiPropertyRegistry`: first in the handler of every client, shared by every device manager, which reads it instead of keeping its own copy. It holds copies of the vectors with their definition metadata, latest state, values, ranges, message, and timestamp, and a revision per vector; never BLOB bytes, only the format and size of the latest delivery.
- `IndiPropertyService` (`api/src/indi.ts`) publishes it for every connection: an `indiserver` speaks INDI natively, and the simulator and the Alpaca client define and update the vectors of their devices and take new values through the same `Client` commands (the Alpaca client translates the vectors it maps into Alpaca calls and ignores writes to the others, which then time out). The directory (`GET /api/connections/:id/indi/devices`, `IndiDeviceSummary`) lists each physical device once by hardware id, including drivers no manager supports, with its driver identification and the connection flag its `CONNECTION` vector reports, never a value; its changes are broadcast as `indi:deviceAdded`, `indi:deviceUpdated`, and `indi:deviceRemoved`.
- The property stream of one physical device (`connectionId`, `hardwareId`) reaches only the sockets that sent `indi:subscribe` for it: an `indi:snapshot` (every vector in driver order and the latest 20 driver messages), then `indi:propertyDefined`, `indi:propertyUpdated` (the changed elements with the vector's current state, message, timestamp, and timeout), `indi:propertyRemoved`, and `indi:message`. A refused subscription gets `indi:subscriptionError` (`notFound`). Subscribing again resends the snapshot; `indi:unsubscribe`, the close of the socket, or the removal of the device end it at once, with no grace period.
- While a device has no subscriber its changes build no payload, serialize nothing, and start no timer. Value-only changes of a vector are coalesced and sent every `VALUE_INTERVAL` (250 ms) with the latest values; definitions, removals, and changes of state, message, range, or timeout are sent at once, carrying the values still pending for that vector. Each stream event carries the `epoch` of its connection's client (new on every reconnection) and a `revision` increasing across the service; each vector carries its own revision. A socket with more than `MAX_BUFFERED_AMOUNT` (1 MiB) queued, or that queued or dropped a send, skips its streams until it drains, then receives a fresh snapshot of each.
- A write (`POST /api/connections/:id/indi/devices/:hardwareId/properties/:vector`, `IndiWriteRequest`) names the revision of the vector the tab shows and is refused as `conflict` (409, with the current `vector`) when the vector changed since; it writes only text, number, and switch vectors the driver does not mark `ro` (`unsupported` otherwise), names only elements the vector has, and sends the whole vector: text and number elements left out keep their current values in a `rw` vector and must be given in a `wo` one, switches are sent as the complete selection, left-out ones off except in a readable `AnyOfMany` vector, with exactly one on for `OneOfMany` and at most one for `AtMostOne` (`invalidParameter` otherwise). Values are not checked against the declared ranges, which the driver applies. It runs as an `indi.propertyWrite` operation under the command contract (202, token, outcome through `operation:updated`). While the device reports being connected it holds the physical device, so it is refused as `busy` while another operation holds it and is cancelled when the device disconnects; a device that is not connected is written without a hold, so its port or `CONNECTION` can be set.
- A write ends with the first update of its vector after it was sent that is not `Busy`: `Ok` or `Idle` succeed, `Alert` fails as `alert` with the driver's message. It times out after the vector's `timeout` plus `WRITE_GRACE` (5 s), 60 s when none is declared and at most 600 s, saying the device may still be working; the deletion or redefinition of the vector meanwhile ends it as `commandFailed` (unknown result), and the removal of the device as `removed`.
- The web view (`web/src/equipment-control/indi/`) is the INDI Properties view of a device in Equipment Control, `/equipment/<device id>/indi`: a device both managed and INDI chooses between Controls and INDI Properties with a selector, a device no interface manages only has INDI Properties. `indiDirectory` mirrors the directory through `SERVER_STORES`; `indiView` is not a server store but the stream of the one device shown: the view subscribes while mounted, its device is in the directory, and the page is visible (a hidden page pauses the subscription and keeps what is shown and the drafts), subscribes again on every socket open, drops events of another epoch or older than what it applied, and unsubscribes when it unmounts or changes device. Vectors are grouped by the driver's groups in driver order (unnamed ones under Other), searchable by group, vector, and element names and labels, in collapsible groups, the first open at first. Text and number vectors are edited in fields (numbers in decimal or sexagesimal, in the driver's units and format, never rounded while typing; write-only fields start empty) and applied with Apply, which sends the edited elements only with the revision shown; `OneOfMany` switches use a select and Apply, `AnyOfMany` checkboxes and Apply, `AtMostOne` action buttons that send at once with an explicit Clear; lights and BLOB metadata are read-only. A draft is never replaced by what the device reports, which is noted as a change on the device, is kept until its write succeeds, and stays after a refusal (a conflict shows the current vector) or a failure; a redefinition of the vector or a new epoch discards it. Each vector shows the outcome of its latest write from `operation:updated`, waiting while the driver works.
- Limitations: success only means the driver ended the change; an update already on its way when the change was sent ends the write too, and a driver may report `Ok` while its hardware still moves, which then no longer holds the device. A driver message without a device, or for a device not seen yet, is not kept.

## Sky Map Contract

- One tick drives the star map and the selection (`#followClock` of `web/src/sky/planetarium.ts`): every `SKY_REALTIME_TICK_MS` (15 s) while the clock follows the real time, every 250 ms while playing, and once for a fixed instant. Each tick reads the instant once, shows it on the map, and refreshes the selection's position and events for that same instant (`refreshSkySelection` with the tick's time): accurately on every real-time tick, from the local models every 2 s while playing, and accurately 400 ms after a fixed instant settles. The time bar's own redraws are display only.
- Picking tolerates fingers: a touch or pen tap picks within `touchPickRadius` (22 px) and stays a tap within `touchTapSlop` (10 px of travel), a mouse click within `pickRadius` (7 px) and `tapSlop` (3 px) (`InteractionOptions` of `web/src/sky/celestial/`).
- On the local sky zoomed in to `SKY_ANCHOR_ZOOM` or more, a tick that changes the instant keeps the view on the same point of the sky (recentered after the update) instead of the same point of the horizon, unless the mount is followed; at lower zoom the horizon stays still.
- Selected objects the map data lacks are remembered for the tab (`RememberedObjects` of `web/src/sky/remembered.ts`, at most `REMEMBERED_LIMIT` = 32, the least recently selected forgotten first, in memory only, kept when the map is replaced by the other kind of chart): minor bodies from SBDB as moving bodies drawn at every zoom whatever their magnitude (`alwaysVisible`), and catalog stars and deep-sky objects fainter than the map data as selectable shapes with their name. They stay drawn and can be selected again on the map. The selected one follows the Inspector's position of each tick; the other minor bodies are moved with local (`fast`) positions at every map update. Satellites are not supported.
- The projection of the map is fixed: the local sky is centred on the observer's zenith and the equatorial chart on its own hemisphere, and no feature ever moves the projection centre or reprojects the map around a coordinate. "Centre on" a coordinate (the mount, a coordinate or footprint sent from an image) only pans the screen view with `Planetarium.centerOn`/`Celestial.centerOnCoordinate`, keeping the zoom and orientation; a point the map cannot project (below the local horizon, or outside the hemisphere the equatorial chart projects) leaves the view unchanged and is said to be so.
- Handoffs from a solved image (`web/src/sky/footprint.ts`, `skyImageState`, tab memory): Open Coordinates in Sky (the image context menu, and the details of a marker) marks a position and pans to it; Show Footprint in Sky (Images → Plate Solver) draws the outline the selected solution gives to the image borders (24 points per side, broken where the WCS cannot unproject) as a dashed shape of its own beside the framing, with a cross at its centre, and pans to that centre. Both keep their positions in the J2000 (ICRS or FK5 J2000) frame of the solution and are converted for the map with the toolkit's IAU 2006/2000A precession-nutation matrix at the instant the catalogs were computed for (`ofDateMatrix`, the conversion of `api/src/sky/catalog.ts`), so they line up with the stars drawn; the matrix is computed once per map data load, never per tick, and nothing is requested. A footprint is drawn only while its document still shows that image and is dropped otherwise (the document closed, or its camera tab shows another frame); the mark stays until replaced or cleared from the Sky toolbar, which also hides the footprint. Neither changes the Sky selection, the clock, or the mount.
- `POST /api/sky/position` returns the rise, transit, and set for an observer in both modes (they are computed locally and cached per hour), so the Visibility of the Object Inspector always shows the instant of its Position.

## Sun Inspector Contract

- Solar almanac (`api/src/sky/sun.ts`, `POST /api/sky/sun/almanac`): a stateless, read-only computation from the toolkit, never the network. For an instant (Unix milliseconds), an observer, and an IANA time zone it answers the Sun's day on the observer's civil date of that instant (`localDay`, absent without an observer), the next four equinoxes and solstices strictly after the instant (named `marchEquinox`, `juneSolstice`, `septemberEquinox`, `decemberSolstice`, so the names hold in both hemispheres), and the equation of time and the Carrington rotation in progress at the instant.
- The civil date is the time zone's, with its real bounds (`zonedDay`): a day the clocks change is 23 or 25 hours long, and a skipped midnight starts the day when the clocks jump. Sunrise, transit, sunset, the daylight (the time above the sunrise threshold within the day), the civil, nautical, and astronomical twilight, and the astronomical night (from the day's astronomical dusk to the next astronomical dawn within 36 hours) use the toolkit's almanac convention: the geometric, geocentric altitude of the Sun's center against `SUN_HORIZON` (−50′) and −6°, −12°, and −18°. This differs by seconds from the rise and set of `POST /api/sky/position` (the upper limb against the refracted topocentric altitude, nearest events within ±12 h), which other objects keep.
- A threshold the Sun crosses both ways is `normal`, one way `partial`, and not at all `continuousAbove` or `continuousBelow`; the first upward and the last downward crossings are kept. Absent crossings, daylight, and durations are absent, never 0. The equation of time uses the Sun's apparent geocentric right ascension of date (nutation and aberration), never the observer's topocentric one. Local days are cached (the latest 64 by date, zone, and observer).
- Observation sources: the latest SDO image (`api/src/sky/sdo.ts`, `GET /api/sky/sun/image?channel&size`) and the latest NOAA SWPC active region report (`api/src/sky/activeregions.ts`, `GET /api/sky/sun/active-regions`) are current real-world observations, never tied to the Sky clock. The image is one of the fixed public JPEGs of the SDO `latest` directory, chosen from an allowlist of channels (`aia193`, `aia171`, `aia304`, `hmiIntensitygram` = HMI colored intensitygram, `hmiMagnetogram`) and sizes (512, 1024), so no URL is built from a request. SDO tells only when a file was modified (`Last-Modified`), never when it was observed, so the route answers that time and the download time (`X-Sun-Fetched-At`) as headers, and the client calls it the update time. The NOAA feed keeps a month of daily records; the report is the records of its latest observed date, one per region, with null fields absent; its spot counts are per group, never the international sunspot number.
- Both sources go through `RemoteCache` (`api/src/sky/remote.ts`): fresh for 15 minutes (images) or 30 minutes (report), one download shared by concurrent requests, a 15 s timeout, a 4 MB limit, and a content type check. When a download fails the last good value is answered marked stale (`X-Sun-Stale: 1`, `stale: true`), without downloading again for a minute; with none, `502 upstreamUnavailable`. A failure of one source never affects the other nor the almanac.
- Sun Inspector (`web/src/sky/sun/`): the Object Inspector of the body `10` (`SunInspector`, dispatched by `ObjectInspector`); no Sky panel view or navigation entry of its own, and no lunar data. Under the name its magnitude and the latest SDO image (`SolarImage`: a channel selector, the update and download times in UTC, a stale image said to be one, a larger 1024 px image in a `Modal` on a click), then the actions of every object (`ObjectActions`), then Active Regions (one row per region, its details on a click), Position with the apparent angular diameter (`2·asin(SUN_RADIUS_AU / distance)`, the distance of the position shown), Visibility (refracted altitude and azimuth of the position, then the sunrise, transit, sunset, and daylight of the almanac's local day), Twilight, Next Solar Eclipse, Seasons (the hemisphere's season named only with an observer), and Solar Physical Data.
- Three times are kept apart: the position and the almanac follow the instant the Sky shows (`selection.position.time`), the day is the observer's civil date of that instant in its time zone (the browser's when it has none), and the image and the report are the latest real observations, dated by their sources, whatever the clock shows. The store (`sun.ts`, `sunState`, tab memory) asks for the almanac only when the observer, the zone, the civil date, or the 10-minute bucket of the instant changes, or the instant passes the next season; for the next eclipse (`/api/eclipses/solar?direction=next`, and `/:id/local` with an observer) only when the instant leaves the interval from the search instant to the eclipse's maximum or the observer changes; and for the image and the report on mount and every 15 minutes while shown. Each resource has its own request guard, loading, and error. A value of another day, zone, or observer is cleared at once. View Eclipse Map opens `/tools/solar-eclipse-map/<eclipse id>` of the eclipse shown. Slew to Object is the generic action: nothing refuses pointing at the Sun, in the inspector or in `api`.

## Moon Inspector Contract

- Lunar almanac (`api/src/sky/moon.ts`, `POST /api/sky/moon/almanac`): a stateless, read-only computation from the toolkit, never the network. For an instant (Unix milliseconds) and an optional observer it answers the Moon's appearance (`MoonAppearance`), the next four principal phases strictly after the instant in time order, and the next perigee and apogee strictly after it with their geocentric distance (km) and apparent diameter. The appearance is topocentric with an observer and geocentric without one: the illuminated fraction and phase angle, the phase name (a principal phase within ±6.1°, half a day of mean synodic motion, of its geocentric Moon−Sun ecliptic longitude difference, otherwise crescent or gibbous, waxing below 180°), the age since the previous geocentric new Moon, the Brown lunation number, distance, apparent diameter (IAU mean radius 1737.4 km), horizontal parallax, the sub-observer point (optical, physical, and with an observer diurnal libration) and sub-solar point (east longitude in (−π, π]), the Sun's selenographic colongitude, the position angles of the pole and of the bright limb, and with an observer the parallactic angle. `bodyToCamera` is the one rotation a renderer needs: from the Moon's IAU body-fixed frame at the light-time retarded instant to a north-up view frame (+X celestial west, +Y celestial north of date, +Z toward the observer), composed from the light-time corrected observer→Moon direction and `bodyFixedMatrix(MOON_ROTATION)`; `sunDirection` is the Moon→Sun unit vector in the body-fixed frame. A zenith-up view is the north-up one rotated by −parallacticAngle. The Moon is ELPMPP02 with VSOP87E for the Earth and the Sun and the IAU rotation model, and the phases and apsides are Meeus' series, so the values may differ slightly from the Horizons-sourced `SkyPosition` of the selection, whose illuminated fraction is the Position section's. The calendar is cached by the interval in which it holds (from the previous new Moon until the first event), so it is computed again after an event or when the instant moves back; the appearance is computed for the exact instant every time.
- Moon Inspector (`web/src/sky/moon/`): the Object Inspector of the body `301` (`MoonInspector`, dispatched by `ObjectInspector`); no Sky panel view or navigation entry of its own. Under the name its magnitude when known and a drawing of the Moon (`MoonImage`), its phase name and illuminated fraction, and how it is oriented ("From the observer · Zenith up", or "From the Earth's center · North up" without an observer), the NASA credit, and a larger view in a `Modal` on a click (the Lunar Surface Explorer below); then Show Framing and Slew to Object. Then Position (with the apparent angular diameter from the position's distance), Visibility (the generic `ObserverSection`: altitude, azimuth, rise, transit, set), Lunar Phases (`lunarPhases`), Perigee & Apogee (`lunarApsides`), Next Lunar Eclipse (`eclipse`: type, greatest eclipse, magnitude, the local visibility of `/api/eclipses/lunar/:id/local` with an observer, and View Lunar Eclipse Map, which opens `/tools/lunar-eclipse-map/<eclipse id>`), and Lunar Physical Data (`physical`: age, lunation, distance, apparent diameter, libration, colongitude, sub-solar latitude, pole and bright-limb position angles, parallax, parallactic angle).
- The drawing (`MoonCanvas`, `moon.renderer.ts`) is the texture on an orthographic sphere through `moon.geometry.ts`: the API's `bodyToCamera`, turned by −parallacticAngle for zenith up, a viewport in CSS pixels, and a soft terminator from `sunDirection` with a faint earthshine; the shading is illustrative, not photometric. WebGL2 draws it with one fragment shader that inverts the projection per pixel, only when the appearance, orientation, size, or view changes; without WebGL2 the same functions run on the CPU at up to 768 pixels on a side, so the drawing and any marker drawn through `moon.geometry.ts` stay aligned. A lost WebGL context is restored and drawn again; the renderer is disposed with the canvas. The store (`moon.ts`, `moonState`, tab memory) asks for the almanac at every new instant of the selection (the Sky's own refresh cadence) and keeps the last drawing of the same observer faded while the next loads, clears it at once for another observer, discards late answers through request guards, and asks for the eclipse only when the instant leaves the interval its search covers; an almanac error never hides the eclipse, and the reverse.
- Lunar Surface Explorer (`MoonImageModal`, the larger view of the Moon drawing): the 4K map zoomed with the wheel or a pinch (1× to 32×) and panned by dragging (`celestial/gesture.ts`), Zenith up / North up, a category filter (all, craters, maria and plains, mountains, rilles and valleys, other), names on or off, and Whole Moon. The catalog (`moon.features.json.gz`) is fetched and unzipped on the first opening, kept out of the proxy (`moonState.features`), and its absence or failure only disables the names. Markers (`MoonFeaturesOverlay`, `featureMarkers` in `moon.features.ts`) are SVG dots at the official center points drawn through the same view matrix and viewport as the texture, so they stay aligned under zoom, pan, orientation, libration, and time; points on the far hemisphere are never drawn, and those on the night side are dimmed. A feature is drawn when its catalog dimension spans at least 16 CSS pixels (20 for satellite craters), by priority (apparent size times a category weight favoring maria and mountains), at most 300 at once, and labels go to markers whose label box overlaps no label or marker of a higher priority, at most 80, on the right of the marker or on its left near the edge; the selected feature is always drawn and labeled. The search ignores case and diacritics, lists names starting with the text first and visible features before those turned away (marked "Not visible now"), and centers and zooms on a visible result. The details (`MoonFeatureDetails`) give the official name, descriptor, center, the approximate diameter or, for elongated features, length, the approval year, the origin of the name, whether the center is on the visible hemisphere and in daylight now (a feature that turns away keeps its details), a link to its Gazetteer page, and the NASA and USGS/IAU credits. Zoom, pan, filter, names, search, and selection are presentation state of the tab (`moonState.explorer`, the view's own transform); none changes the observer or the instant. Center points are markers, never outlines or measured extents; no elevation is shown.
- Moon assets (`web/assets/moon/`, generated by `bun make:moon` from `bin/src/moon.assets.ts`, not committed): `moon.2k.jpg` is the NASA SVS CGI Moon Kit LROC color map (https://svs.gsfc.nasa.gov/4720/, 2025 version) copied unchanged at 2048×1024; `moon.4k.jpg` is its 16-bit sRGB 4096×2048 TIFF reduced to 8 bits and encoded with the toolkit's TurboJPEG (about 1.9 MB). Both are equirectangular, centered on 0° longitude, east to the right, north up, and illustrative: NASA optimizes them for appearance, not science, and fills latitudes beyond ±70° with LOLA albedo. `moon.features.json.gz` (the gzipped JSON `MoonFeatureCatalog` of `api/src/sky/moon.features.ts`, about 260 KB, 1.2 MB unzipped) holds every IAU-adopted lunar surface feature of the USGS Gazetteer of Planetary Nomenclature center-point archive (`MOON_nomenclature_center_pts.zip`, about 9 100 names) as positional rows: Gazetteer id, official name with its diacritics, official descriptor, explorer category, satellite and elongated flags, planetocentric latitude and east longitude in degrees in [-180, 180) (converted once from the archive's [0, 360)), the approximate diameter or longest extent in km, the approval year, and the origin of the name. Center points are markers, never outlines. `moon.provenance.json` records each source's URL, SHA-256, size, and download time, each output, and the credits. The generator reads the archive's ZIP, DBF, and the LZW TIFF itself (`bin/src/moon/`), keeps only the status `Adopted by IAU`, fails on an approval status or descriptor it does not know, and writes the records it leaves out and why to `bin/data/moon/moon.features.audit.json`. Sources are downloaded once into `bin/data/moon/` (not committed); updating the assets is deleting them there and running `bun make:moon --force`, never a refresh at run time; outputs whose bytes are unchanged are left alone, and a changed one is replaced only with the development server stopped, since Windows refuses to replace a file it serves. `bun make:moon --empty` writes a gray 2×1 map and an empty catalog without downloading anything.

## Sky Framing Integration Contract

- Framing is a view inside Sky. It reuses the selection, the framing center, and the `OpticalPreset` and `resolveFraming` results of `web/src/sky/framing.ts`: angular size, image scale, and position angle measured from north through east. Its Equipment Setup source combines the sensor of a camera role or a manual one with the optics that camera looks through (`usesGuideTelescope`): the profile's guide telescope (`guideTelescope`) for the Guide Camera, its telescope otherwise; the panel edits those optics under their name.
- Survey images come from `hips2fits` (`core/src/adapters/sky/hips2fits.ts`) through an `api` proxy route that caches cutouts and survey lists and returns the survey's attribution. Network failure leaves the planetarium framing usable.
- The cutout is requested in TAN projection centered on the framing center, with the preset's FOV and rotation, so its pixels match the gnomonic outline drawn by `framePolygon`. The first Framing task is a test that pins the sign convention of the position angle against a cutout's WCS.
- Pixels are not assumed to be linear in RA/Dec. Any overlay on the survey uses the cutout's WCS.

## Tools Integration Contract

- Navigation: Tools → catalog card → `/tools/<id>`, rendered by the tool's `view` inside its own `WorkspaceLayout`. A tool without a view is planned and its URL returns to the catalog.
- Calculator (`web/src/tools/calculator/`): task-oriented calculators chosen in one menu grouped by category (`catalog.ts`), each composing pure formulas of `nebulosa/src/astronomy/formulas` behind one form, never one entry per formula and no expression engine. The five categories are Optics & Field of View (Imaging Setup: field, diagonal, image scale, effective focal length and ratio through `resolveFraming`, so it matches Sky Framing's 2·atan convention, with no image scale for a sensor given by its physical size; Mosaic Estimator: rectangular panel count per axis with overlap, not an optimized layout), Sampling & Focus (Sampling: FWHM in pixels from the seeing or the seeing from a measured FWHM, the 2–3 px rule-of-thumb class, and the focal length for a target FWHM; Diffraction & Focus: Airy disk and critical focus zone, wavelength in nanometers), Exposure & Integration (Exposure Planner: total integration from a frame count or whole frames for a target time, with the idealized √N and 1.25·log₁₀N stacking gains; Star Trailing: sidereal drift of an untracked star and the longest exposure within a trail budget, none at a celestial pole), Visual Observation (Eyepiece & Telescope: magnification, exit pupil, true field from the apparent field or the field stop, Dawes and Rayleigh limits, limiting magnitude; Aperture Comparison: clear light grasp and the collecting area left by central obstructions, never presented as resolution), and Atmosphere & Conditions (Airmass & Visibility Effects: Kasten–Young airmass, extinction for a coefficient, Sæmundsson refraction; Dew Conditions: Magnus dew point with the heuristic ambient-margin risk, humidity from a dew point, or frost point from a humidity relative to ice). Each calculator shows its formula, units, domain, and approximations; mode switches fix the direction of a calculation so fields never depend on each other circularly. Camera & Signal and Guiding & Tracking calculators are not provided yet. Everything runs in the browser: no route, event, operation, or device is involved. Fields keep their text as typed and are parsed only at the calculation boundary (`values.ts`), so an empty or out-of-domain field shows what to enter or why it cannot be used instead of a previous result, and no result shows NaN or Infinity. Each calculator keeps a draft in React state while the tool is open; drafts start from labeled examples and are never persisted, and a change of active profile starts over. An optical configuration can be imported by value (`sources.ts`) from the Main or Guide Camera (the telescope or guide telescope with the sensor that camera reports, never another camera's), from the Sky Framing manual sensor (refused when none is entered), or from an optical preset; the draft is then edited on its own, live changes never rewrite it, its origin is shown only while the same camera is followed, and the profile, presets, and devices are never written.
- Eclipse maps: computed in `api` from `core/src/astronomy/events/eclipse/*`, which already produce geographic geometry and SVG paths, drawn on `WorldMap` (see World Map Contract). No map library is added.
- Lunar eclipses (`api/src/lunareclipses.ts`): stateless, read-only queries, never operations or events. The id, the degree plane, and the location parameters are the eclipse conventions of `api/src/eclipses.ts`. An eclipse is named by its id, the Unix milliseconds of its greatest eclipse, resolved again on every request (an id that names no eclipse is `404 notFound`), so nothing is stored per client. `GET /api/eclipses/lunar` steps to the next or previous eclipse from an instant, strictly, so stepping from an id never returns the same eclipse; with a place, it skips eclipses whose Moon stays below its horizon, trying 24 eclipses at most and letting the event loop run between them. `/:id/map` answers the contact times, sublunar points, and per-contact moonrise/moonset lines and above-horizon regions as SVG path data on a degree plane (x = longitude + 180, y = 90 − latitude); `/:id/local` answers the circumstances of a place (visibility over the whole eclipse, contact altitudes, azimuths, P and Z angles, magnitudes, durations) and the Local View's shapes. Times are Unix milliseconds (UTC, converted from the toolkit's TT), angles degrees, durations seconds; contacts an eclipse lacks are absent. Visibility is the Moon's center at or above the geometric 0° horizon without refraction, on the map and locally alike. Whole-eclipse visibility zones on the map are not provided: the map shows visibility at one contact.
- Solar eclipses (`api/src/solareclipses.ts`, `solareclipses.map.ts`): stateless, read-only queries with the lunar conventions of `api/src/eclipses.ts` (id, strict stepping, `404 notFound`), never operations or events. `GET /api/eclipses/solar` steps to the next or previous eclipse; with a place, it skips eclipses whose Sun stays below its horizon during the local eclipse, trying 48 eclipses at most and letting the event loop run between them. `/:id/map` answers the named global points (P1–P4, U1–U4, C1/C2 the ends of the central line, MAX, N1/N2/S1/S2) with their times and the Sun's geometric altitude there, the greatest eclipse and greatest duration, and SVG path data on the degree plane for the total and annular parts of the central line (split where a hybrid eclipse changes), the northern and southern limits of the central and partial eclipse, and the sunrise/sunset curves; separate branches stay separate subpaths. A map costs hundreds of milliseconds, so it is computed on a worker of its own (`api/src/solareclipses.worker.ts`, embedded by `app/build.ts`), one at a time, with concurrent requests for one id sharing a job, a 30 s timeout (`500 computationFailed`), and the latest 8 maps cached. `/:id/local` answers the circumstances of a place computed in the API process with the same ephemeris as the map's Besselian elements: visibility (kind, central phase, Sun rising or setting, completeness of the contacts), C1, C2, MAX, C3, C4 with the Sun's altitude, P and Z, and magnitude, the maximum magnitude, Moon/Sun diameter ratio, partial and central durations, the central shadow's chord through the place (not the path width), and the Local View's shapes. Times are Unix milliseconds (UTC, converted from the toolkit's TT), angles degrees, durations seconds, widths kilometers; values an eclipse or a place lacks are absent. Locally, visible means the Sun's center at or above the 0° horizon, without the site's elevation, terrain, or the lunar limb profile; the map's limits use the toolkit's empirical horizon refraction, matching the NASA maps. Obscuration zones and animation of the shadow are not provided.
- Lunar Eclipse Map (`web/src/tools/lunareclipse/`): its state is a tab-lived valtio proxy (`lunarEclipseState`), never persisted, so leaving and reopening the tool keeps the eclipse, the place, and the presentation. It opens on the next eclipse after the real current time, never the Sky simulation clock, unless its URL names an eclipse, and takes the active profile's Sky observer as the place when there is one; a click on the map or coordinates typed in replace the place for the tool only, never the profile. A click asks only for the local circumstances; choosing a contact or a Local View presentation asks only for them again, and zooming or panning asks for nothing. Stale answers are discarded through request guards. Times show the date and the zone's name: the chosen zone, otherwise the observer's zone for the observer and UTC for any other place, since a coordinate does not tell its civil time zone. The place, time zone, and time formatting rules, the Location section, and the map's heading and legend are shared by the eclipse tools in `web/src/tools/eclipse/`; below the sm breakpoint the heading puts the eclipse type and date on two lines and the legend starts collapsed to a button. A URL that names an eclipse (`/tools/lunar-eclipse-map/<eclipse id>`, the id of `/api/eclipses/lunar`) shows that eclipse with its map (`showLunarEclipse`), with the same rules as the Solar Eclipse Map's link: shown whatever the tab showed before, on a link, a reload, back, or forward; an id that names no eclipse shows the error; stepping replaces the id in the URL.
- Solar Eclipse Map (`web/src/tools/solareclipse/`): built like the Lunar Eclipse Map, with a tab-lived valtio proxy (`solarEclipseState`), the shared place and time zone rules, and request guards. Its global map does not depend on a contact or a place, so a click or a contact asks only for the local circumstances again, and showing or hiding a layer (central line, central limits, partial limits, sunrise/sunset curves, points; all but the sunrise/sunset curves shown at first) asks for nothing. The central line is solid where total and dashed where annular, so a hybrid eclipse reads without color. Every global point is drawn with its name (a layer of its own), with a marker shape per family, and the names of points that nearly coincide are stacked. A global point is chosen in the panel's Global Points list, since a click on the map chooses the place; the map then rings it and centers on it, and the panel tells what it is, where and when, the Sun's altitude, and for the greatest eclipse and duration the Sun's azimuth, the central phase, its duration, and the path width, and can make it the place. Global points are named apart from the local contacts: C1 and C2 on the map are the ends of the central path, never the contacts of a place. Contacts, durations, and the shadow chord a place lacks are left out, and the magnitude is a fraction of the solar diameter, never an obscured area. A URL that names an eclipse (`/tools/solar-eclipse-map/<eclipse id>`, the id of `/api/eclipses/solar`) shows that eclipse with its map (`showEclipse`, under the same request guard as the searches), whatever the tab showed before, on a link, a reload, back, or forward; an id that names no eclipse shows the error, never another eclipse. Stepping to another eclipse from such a URL replaces it with the new id, so the URL never names an eclipse other than the one shown; without an id the tool keeps its own choice.
- Mount Remote Control (`api/src/mountremotecontrol.ts`, `web/src/tools/mountremotecontrol/`): exposes the MOUNT of the active profile's Equipment Setup to planetarium programs through `Lx200ProtocolServer` and `StellariumProtocolServer`. The tool never chooses a mount: without a MOUNT, or with one that is unavailable, disconnected, or switching, Start is disabled with the reason, and Equipment Setup is offered. A listener exists per (open connection id, exact mount id, protocol), so one mount may run an LX200 and a Stellarium listener at once and several mounts may be exposed by different tabs; the registry is process-wide, never per tab or profile, and switching profile, setup, or workspace, or closing the tab, never stops or redirects one. `POST …/remote-control/:protocol/start` with `{ host, port }` answers the listener (`MountRemoteServer`); a repeated start with the same binding answers it again, another binding is `409 conflict`, a taken address `409 addressInUse`, another bind failure `500 bindFailed`, and a failed start leaves the other listeners running. `/stop` (idempotent, 204) closes its clients and waits for their manual motions to stop; `DELETE …/clients/:clientId` closes one client (204, also when it already left). A listener stops with its mount (`device:updated` disconnected, `device:removed`) or connection (`connection:close`) and with the process, and is never restarted by itself. `GET /api/mount-remote-control` (`MountRemoteSnapshot`) and `mountRemoteControl:updated` carry an epoch per process and a revision per change, so the mirror (`listeners.ts`, in `SERVER_STORES`) drops a snapshot or start response older than an event it applied. Each client is shown as IP:port with Disconnect, nothing else. Clients are not authenticated; the default binding is `0.0.0.0` (every interface) on 10002 for LX200 and 10001 for Stellarium, and the tool warns whenever the host is not a loopback address. Commands run through the shared `MountCommands` commander and the operation registry, never a second command path: positions are the mount's (equinox of date) converted to J2000 at the server's time; a goto (`goToNow`, the same refusals as the goto route, above the horizon of the site the mount reports) or a sync (`syncNow`) is admitted or refused at once, LX200 answering it (`:MS#` `0` or `1Slew not possible#`, `:CM#` `#` or `Sync failed#`) and Stellarium only logging a refusal, and an admitted goto (`mount.goto`) goes on if its client leaves. An LX200 client's manual motion is its own `mount.remoteMove` operation, its commands run in order, another client's or a nudge's motion refuses it, and it stops when every axis is released, the client disconnects, the listener stops, or after `REMOTE_MOTION_WATCHDOG` (30 s); `:Q#` is the emergency stop of the mount. An LX200 client may set the mount's site (`:St#`, `:Sg#`, such as the GPS position Stellarium Mobile sends): the latitude and longitude are admitted at once, refused (`0`) while the mount is disconnected or held by an operation, and written together through the commander (`mountLocation`) after 250 ms, keeping the elevation; clock commands never change the mount (setters answer `0`), and slew rates are ignored. Stellarium clients receive the position every second. The host and port a listener was last started with are remembered per saved connection, mount, and protocol in the profile (version 10); a running listener always shows its actual binding.
- Alpaca Server: an `api` service over `AlpacaServer`, started and stopped explicitly, bound to localhost by default, publishing only an explicit allowlist of devices. Devices imported from Alpaca connections are never exported, to avoid publication loops. Its state is published as events. The Tools view only controls it.

## External Tools Contract

- External programs and services the backend uses are registered in `api/src/externaltools.ts` with the capabilities their adapters provide and the settings they take (`fields`): ASTAP (plate solving and star detection, through `core/src/astrometry/solvers/astap.ts`; executable), Astrometry.net Local (`solve-field`; executable and an optional backend configuration file naming the index directories), and Nova Astrometry.net (the web service; endpoint, empty for the public one). The native `detectStars` and the libastrometry binding are not external tools: the binding is not integrated, because `solver_run` is one blocking native call that cannot be interrupted and whose crash would take the server down, and because it takes stars already detected, which would need a detection configuration of its own. No route runs an arbitrary command.
- A web service (`session: true`) is signed in to with the API key of an account: `POST /api/settings/external-tools/:id/login` sends the key once to the saved endpoint and stores only the session the service returns; the key is never stored nor logged. `POST …/logout` removes the session, and saving another endpoint signs out. Clients only see `signedIn`; the session itself reaches only the services through `resolve`. A web service is configured when signed in. Its Test checks the endpoint and the saved session without contacting the service, so an expired session is found by the next run.
- Settings belong to the server instance, never to a profile or a browser: Settings (the top bar gear button) → External Tools (`/settings/external-tools/<id>`) edits a draft, and only Save writes it, with the revision it was edited from; a save from an outdated revision is refused with 409, and every change is published as `externalTool:updated`.
- With no executable saved (no session for a web service), a program is Not Configured and `ExternalToolsStore.resolve` returns undefined, so its services must refuse to run it; no platform default path is assumed. A service resolves the settings once when an operation starts and keeps that snapshot until the operation ends, so a save applies to the next operations without a restart.
- Test checks a draft on the server's filesystem without saving it: the path exists, is a regular file, and may be executed (on Windows any existing file passes); a bare name is looked up on the server's PATH; a configuration file, when set, must exist. It never starts the program, so it proves neither that the program runs nor that it analyzes images, and the version is reported as unknown. Only a check of the saved settings becomes the program's latest check, kept in memory until the server restarts.
- There is no authentication: any client that can reach the API can change the executable the server runs and check paths of its filesystem, like `/api/files` lists them. Keep `APP_HOST` on localhost when untrusted clients can reach the network.
- Nothing configured ASTAP before these settings existed, so there is nothing to migrate. The settings of solve-field and nova are optional fields of the same version 1 file.

## Star Detection Contract

- One service, `StarDetectionService` (`api/src/stars.ts`), detects the stars of an image document for every consumer: Images → Star Detection (manual runs) and Auto Focus. Captures never analyze their frames. Results are the toolkit's `DetectedStar` (x, y, HFD, SNR, flux) in 0-based pixel coordinates of the document, origin at the upper-left sample, +X right, +Y down.
- Providers: `builtin` runs `detectStars` on a worker of its own (`api/src/stars.worker.ts`), fed a grayscale copy prepared by the image worker (a CFA mosaic is debayered with its trusted pattern first). `astap` runs `astapDetectStars` on a FITS copy in a per-job temporary directory, with the External Tools settings resolved once per job (or per Auto Focus session). ASTAP failures are typed (unavailable, timeout, failed); a failure never falls back to the other provider.
- Scheduling is in memory, through the `AnalysisScheduler` of `api/src/analysis.ts` shared with the other image analyses: one built-in detection and one ASTAP process at a time, at most 16 jobs waiting, run in arrival order. A running built-in detection is cancelled by terminating its worker; ASTAP is killed through its signal. No device is held.
- Accepted stars have finite coordinates inside the image less an edge margin, a finite positive HFD within the limits, and finite positive SNR (at least the minimum) and flux. The aggregate HFD is the median HFD of the accepted stars, in pixels, and is unavailable (never 0) below 3 accepted stars. HFDs of the two providers are computed differently and must not be compared.
- Jobs are published as `stars:updated` without the stars; `GET /api/stars` is the snapshot, `GET /api/stars/:jobId/result` the full result, `POST /api/images/:id/stars` submits a manual detection (an equivalent kept result is answered instead), and `POST /api/stars/:jobId/cancel` cancels. Results are kept per image (8) and in total (256), in memory only, and dropped when the image is released: an expired result answers 404.
- Image quality (`web/src/stars/quality.ts`, `ImageQualitySummary`) is derived from the latest star detection known for an image id, whoever asked for it, so the HFD an Auto Focus measured on a frame is shown with that frame without detecting again. Its states are `not-measured` (no detection, or the latest was cancelled or skipped), `pending`, `measured` (an HFD only when enough stars were accepted), and `failed`; absence is never zero, and the summary keeps the provider and request an HFD is only comparable under. The Image Inspector shows it in its Quality section; nothing is measured automatically, and per-frame quality history is not kept yet.
- The request (detector, its settings, acceptance) is one profile preference, `ProfileSettings.starDetection` (`starDetectionSettings`, `setStarDetectionSettings` in `web/src/profile/profile.ts`), edited in Images → Star Detection (also before the document has an image, as a camera tab waiting for its first frame, with Run Detection disabled until it has one) and shared by every document and by the frames of Auto Focus and Guiding; a document keeps only how its markers are shown. The built-in detector's "Aperture radius" (`maximumRadius`) defaults to 32 px (`DEFAULT_APERTURE_RADIUS`); the aperture grows only while a star extends beyond it, so focused stars measure as with the fixed 4 px one.
- Auto Focus integration: `StarDetectionService.measure(imageId, request, signal, origin)` resolves to the result of one image, runs with the manual priority, is never replaced by a newer frame, and cancels with its signal; it also takes a preparation resolved once, so a session keeps its ASTAP settings. Auto Focus jobs carry the `autofocus` origin.
- Limitations: results do not survive a restart; the built-in HFD is measured inside a 4 px aperture unless the request sets a larger `maximumRadius` (the web client always sends one, 32 px by default), so with the fixed aperture it saturates near 8 px for defocused stars, and the built-in detector returns at most 2000 stars; saturation is not detected; a frame replaced on screen before its result is fetched shows no markers.

## Streak Detection Contract

- One service, `StreakDetectionService` (`api/src/streaks.ts`), detects the approximately straight streaks of an image document for Images → Streak Detection (manual runs only; no capture, sequence, or other analysis starts one). It runs the toolkit's `detectStreaks` on a worker of its own (`api/src/streaks.worker.ts`), fed `ImageStore.processingImage`: a full copy of the decoded samples in their own precision and layout, mono, RGB, or a CFA mosaic with its trusted pattern, never the debayered luminance copy of Star Detection nor anything the viewer applies (debayering, stretch, inversion, zoom). The analysis plane is `auto` (mono, RGB green, CFA green1) unless the settings name one the image has. Bright pixels whose gradient coherence is below `minCoherence` (stars, hot pixels) neither vote nor count in the photometry, so a trail crossing a crowded field is found; 0 keeps them, which a dotted trail of dashes shorter than about 7 px needs. The width is measured from the profile core on the fitted axis, and a line whose corridor holds a brighter structure beside the axis is rejected; a streak supported over less than `minCoverage` (0.5) of its length is rejected too, so a dashed trail needs a lower value.
- A `Streak` is in 0-based pixel coordinates of the received image (origin at the upper-left sample, +X right, +Y down), even on a CFA plane; its axial angle is in radians in [0, π), shown in degrees. The whole image is analyzed (no ROI), and the saturation level is never sent: the toolkit compares it with normalized samples. Photometry is in normalized sample units; an absent SNR or saturation fraction stays absent, never 0.
- The worker then classifies the streaks with `classifyStreaks`, from evidence of the same image only: its samples, its exposure and DATE-OBS, its WCS, and the accepted stars of a star detection. The WCS is the solution of the completed plate solving job of the image the request names (`plateSolveJobId`), else the valid WCS of its header; the stars are those of the completed star detection job of the image the request names (`starDetectionJobId`). The service resolves them through `PlateSolvingService.result`/`solutions` and `StarDetectionService.result` when the job is submitted and freezes them, so a later solve or detection never changes a job; a named job unknown, no longer kept, of another image, or without a solution is refused (422 `contextUnavailable`). Nothing is solved or detected for the classification, and no ephemeris, radiant, tracking quality, prior frame, network, or catalog is used. Each job publishes the sources it used (`context`).
- A classification is the toolkit's uncalibrated evidence weight: `unknown` unless the evidence singles out a class, and never shown as a probability. It is kept apart from the detector's `confidence`, by index in `classifications`. A classification that throws leaves the streaks unclassified (`classified: false`, a warning) instead of failing the job.
- Scheduling uses the shared `AnalysisScheduler`: one detection at a time, at most 16 jobs waiting. An equivalent request (image, every detector setting, context job ids) is answered with the job still waiting or running, or with its kept result. A running detection is cancelled, or stopped after 120 s (`timeout`), by terminating its worker. The settings are not validated by the API: the toolkit refuses invalid ones or a job beyond its bounded Hough work, and the job fails as `detectionFailed` with its reason, while a job beyond its bounded refinement work completes with the streaks refined so far; the web form keeps every setting within the toolkit's ranges and the orientation tolerance within 16 steps of the angle step.
- Jobs are published as `streaks:updated` without the streaks; `GET /api/streaks` is the snapshot, `GET /api/streaks/:jobId/result` the full result, `POST /api/images/:id/streaks` submits (202, or 200 for a kept equivalent result), `GET /api/images/:id/streaks` lists the kept jobs of an image, and `POST /api/streaks/:jobId/cancel` cancels. Results are kept per image (8) and in total (256), in memory only, and dropped when the image is released.
- The detector settings are one profile preference, `ProfileSettings.streakDetection` (`streakDetectionSettings`, `setStreakDetectionSettings`; version 12), shared by every document and editable before a camera tab has a frame. Whether the next detection uses the plate solution shown and the latest stars of the image, how the lines are drawn, and the selected streak belong to the document view (`ImageStreaksState`). Run Detection holds the frame a camera tab shows. The lines (`web/src/streaks/StreakOverlay.tsx`) are drawn only over the image their result measured, without arrows; a click on a line (within 8 screen pixels) or a row of the list selects the same streak, and the selection of a camera tab is cleared when another frame is committed.
- Limitations: results do not survive a restart; chance alignments of stars in a very crowded field can be reported as streaks, more often with a small max width, and a trail among an extreme density of stars can be split; a detection cut short by the refinement budget is not flagged; there is no ROI, mask (`createStreakMask`), reclassification of a kept result, satellite or solar-system prediction, meteor radiant, tracking quality, or classification across frames.

## Annotation Contract

- One service, `AnnotationService` (`api/src/annotations.ts`), identifies what an image document shows from its WCS, never from its pixels (manual runs only). The WCS is the solution of the completed plate solving job of the image the request names (`plateSolveJobId`), else the valid WCS of its header (`PlateSolvingService.result`/`solutions`), resolved and frozen when the job is submitted; a named job unknown, no longer kept, of another image, or without a solution, an image without a usable WCS, or a WCS that cannot unproject the image is refused (422 `contextUnavailable`). Nothing is solved implicitly, and a local job queries no network.
- The field is the cone around the unprojected image center that holds 8 unprojected points along each side (`annotationField`), plus 1′ for proper motion. The embedded sky catalog is scanned in memory for it (`fieldObjects`, `fieldConstellations` in `api/src/sky/catalog.ts`, behind the narrow `annotationSky` of `api/src/sky/index.ts`; a few milliseconds for the whole catalog, so the catalog has no spatial index): the stars and deep-sky objects up to the request's `magnitudeLimit`, deep-sky objects of a classic visual catalog without a magnitude too, at most 2000 of each (brightest first, `truncated` when more), and the stick figures with a segment reaching the cone, whole, with the labels inside it. An object is kept when `tanProject` puts it on the image; a deep-sky object when its major axis may reach the image.
- Positions are astrometric on the ICRS (J2000) equator of a plate solution, never apparent of date: deep-sky objects keep their catalog position, and stars are moved linearly by their proper motion to the observation instant. A local job has no solar-system body: the Sun, the Moon, the planets, and their satellites come from the solar-system search with the asteroids and comets.
- The observation context (`observationContext`) always comes from the image, for both kinds; a request carries no instant or observer. The instant is the middle of the exposure from the raw DATE-OBS of the header, else from its DATE-END when the exposure (EXPTIME or EXPOSURE) is known; FITS dates are UTC, and a date resolved to more than a second only is `approximate`. Without one, a local job moves the stars to the current time (origin `now`, with a warning) and a solar-system search is refused; a camera frame's command instant is not a fallback. The site is that of the header (OBSGEO-X/Y/Z, OBSGEO-B/L/H, or SITELAT/SITELONG/SITEELEV, read by the toolkit's `readFitsTime`), else the Earth's center.
- Scheduling uses the shared `AnalysisScheduler`: one annotation at a time, at most 16 jobs waiting. An equivalent request (image, kind, WCS job, and the magnitude limit of a local job or the groups of a solar-system search) is answered with the job still waiting or running, or with its kept result. Jobs are published as `annotations:updated` without the objects; `GET /api/annotations` is the snapshot, `GET /api/annotations/:jobId/result` the full result, `POST /api/images/:id/annotations` submits (202, or 200 for a kept equivalent result), `GET /api/images/:id/annotations` lists the kept jobs of an image, and `POST /api/annotations/:jobId/cancel` cancels. Results are kept per image (8) and in total (256), in memory only, and dropped when the image is released.
- A result carries the WCS it was computed with (`solution`), so a client projects the objects with the same one, the field, the observation context, and each object's stable id (`catalog:<id>`, `body:<code>`, `satellite:<number>`, `skybot:<number or designation>`), its `SkyObjectRef`, layer, names, magnitude, and size and position angle when the catalog has them; never pixels, screen positions, or SVG.
- Images → Annotation (`web/src/images/AnnotationPanel.tsx`, mirrored by `web/src/annotations/annotations.ts` in `SERVER_STORES`) sends the plate solution shown when it is a completed job of the image, else annotates with the header's WCS; Run Analysis is disabled without either and holds the frame a camera tab shows. The overlay (`web/src/annotations/AnnotationOverlay.tsx`) is drawn only over the image its result annotated and only while the solution shown is the one it was computed with (`annotationMatchesWcs`). Its geometry (`web/src/annotations/geometry.ts`) is computed once per result through `pointAt`: the outline of a deep-sky object is an ellipse of its catalog axes and position angle sampled on the sphere and then projected (a dashed circle of the major axis without an orientation or minor axis, a marker below 10 screen pixels), constellation figures are sampled along great circles, broken where the projection fails or jumps, and clipped to the image, and a body's predicted motion during the exposure is a dashed segment. Zoom and pan only place the labels again: a greedy, deterministic pass by priority (bodies, deep-sky objects, stars, then magnitude; the selected object first) over a spatial grid, within a budget per density (15, 40, 150), never over a marker. Groups (deep-sky objects, stars, the Sun, Moon, and planets, satellites, asteroids and comets, constellation lines and names), labels, density, outlines, motion, the magnitude limit (a lower one filters at once, a higher one applies to the next run), the groups the next solar-system search lists, and the selected object (by result job and object id) belong to the document view (`ImageAnnotationState`), so nothing of the overlay runs an analysis; a click within 8 screen pixels of a marker, or inside the extent of an object, and a row of the list select the same object, and the selection of a camera tab is cleared when another frame is committed. Open in Sky selects the object's `SkyObjectRef` in the Object Inspector and opens the Sky workspace without changing its time.
- A solar-system search (`kind: solarSystemBodies`, Find) is a separate job of the same routes and events, run by its own provider (`skybot`, one at a time) so it never waits for nor delays a local annotation. It asks the IMCCE SkyBoT cone search (`coneSearch` of `core/src/adapters/orbits/skybot.ts`) for the solar-system objects of the same cone at the observation instant, always from the geocenter (code 500): SkyBoT refuses a geographic observer on every interface despite its documentation. The request's `bodies` choose the groups listed, every one by default: `solarSystem` (the Sun, the Moon, and the planets, SkyBoT classes Star and Planet and the satellite Moon, which take the `SkyObjectRef` and the id of their body in the sky API, so they open in the Sky workspace), `satellite` (the other natural satellites), and `minorBody` (asteroids, dwarf planets, and comets); SkyBoT's object filter asks only for the classes needed, and the Sun, the planets, and the satellites, which it lists together, are sorted afterwards. When the header locates the image, every position, the motion ends included, is moved by the parallax of that site at its own instant (`geocentricToTopocentric` of `core/src/astronomy/coordinates/astrometry.ts`) from SkyBoT's geocentric distance; without a site, or for a body without a distance, it stays geocentric, with a warning. The search runs within 20 s (`timeout`; a failure of the service is `providerFailed`; cancelling aborts the request); no retry, fallback to another service, or background search exists. It is refused at submit (422 `contextUnavailable`) without an observation date, outside SkyBoT's epochs (1889 to 2060), for a cone beyond its 10° radius, or with no group. Kept objects are those on the image, at most 1000, brightest first, with SkyBoT's J2000 position, magnitude, position uncertainty, and motion during the exposure from its rates; a satellite or minor body has no `SkyObjectRef`: SkyBoT gives no SPK-ID. The magnitude limit never filters them. Every position says where it is seen from (`center` of the object and of the observation: `geocentricCorrected` computed for the geocenter and moved by the parallax of the site, `geocentric`), so a fallback is never shown as a topocentric prediction, and the observation carries the `site` used (latitude, longitude, elevation, and the keywords it came from). `GET /api/images/:id/annotations/context` gives the observation date and site of an image header (`AnnotationImageContext`) before any run. In the panel, Source & Status shows that date (UTC, with its keyword, or the current time without one) and the site with its keywords, the Solar System Bodies section the groups to list and how the positions will be seen; Find is disabled for an image without an observation date or with no group chosen. Its objects are listed and drawn with the local ones (the Sun, Moon, and planets as a diamond, a satellite as a smaller one, an asteroid or comet as a cross, the uncertainty as a dashed circle once larger than the marker); a satellite does not open in the Sky workspace, and Find in SBDB and Open in Sky looks the selected minor body up by its number or designation (`/api/sky/minorbodies/search`) and opens it only when SBDB knows exactly one body; a match is never guessed from a position.
- Limitations: results do not survive a restart; the catalog is not complete to any magnitude, and the stars are those of the embedded catalog only; solar-system bodies need the network and SkyBoT, and their positions are predictions, not detections; no artificial satellites or nebula outlines; without a site in the header the Moon may be up to a degree off; the outline of a deep-sky object is the ellipse of its catalog axes, a dashed circle without an orientation; Open in Sky shows the object at the time of the Sky workspace, not of the image; there is no annotated image export (the overlay is drawn by the viewer only, and Save As writes the scientific pixels unchanged).

## Plate Solving Contract

- One service, `PlateSolvingService` (`api/src/platesolving.ts`), solves an image document for every consumer: Images → Plate Solver and TPPA. Captures never solve their frames. Providers are ASTAP, Astrometry.net Local (`solve-field`), and Nova Astrometry.net, each resolved once per job from External Tools; a request never names an executable or a URL. A provider never falls back to another, so a local failure never uploads an image. The libastrometry FFI binding is not a provider (see External Tools Contract).
- Strategies: `assisted` searches around a position, `blind` over the whole sky. Hints (`api/src/platesolving.hints.ts`) come from the operator, then from the header pointing (RA/DEC, OBJCTRA/OBJCTDEC, RA_OBJ/DEC_OBJ, CRVAL1/CRVAL2) and the optics (XPIXSZ after binning over FOCALLEN); a position without a radius gets 10°. A blind solve sends no position but keeps a known scale, and its FITS copy leaves the pointing keywords out so ASTAP cannot use them. The current mount position is never a hint; a mount pointing session hints the position it commanded, explicitly. Every job keeps the hints it used with their origins. Angles are radians; the scale is radians per pixel.
- A result keeps the whole WCS header of the solver as the toolkit's `PlateSolution` (ICRS center, scale, orientation, parity, field size). It is accepted only when `plateSolutionFrom` proves it (equatorial TAN or TAN-SIP, ICRS or FK5 J2000) and its image size is the document's, within 1 px (ASTAP rebuilds NAXIS from CRPIX); otherwise the job fails as `invalidSolution`. A solver that ended normally without a WCS completes with `outcome: noSolution`, which is not a failure. The WCS a header already had is reported apart (`GET /api/images/:id/plate-solutions`, `header`) and never replaced; no file is written.
- Scheduling uses the shared `AnalysisScheduler`: one ASTAP and one solve-field process and two nova solves at a time, at most 16 jobs waiting, run in arrival order, results kept per image (8) and in total (256) in memory only. An equivalent request (image, provider, strategy, effective hints, tolerance, downsampling, provider settings) is answered with the job still waiting or running, or with its kept result, so a double click, a second tab, or a retry never solves twice. No device is held, and the service never syncs, slews, or centers a mount.
- Nova (`api/src/platesolving.nova.ts`) uploads the FITS copy once, as a private submission, publishes the stages `uploading`, `submitted` (submission id), `solving` (job id), and `retrieving`, polls every 5 s, and gives up after 3 failed requests in a row (`network`) or at the provider timeout. An upload refused for its session is `sessionExpired`. Cancel stops following the remote job only, and says so. Jobs, and the following of a nova job, do not survive a restart, and nothing is uploaded again.
- Jobs are published as `plateSolving:updated` without the WCS; `GET /api/plate-solving` is the snapshot, `GET /api/plate-solving/:jobId/result` the full result, `POST /api/images/:id/plate-solving` submits (202, or 200 for an equivalent job), `GET /api/images/:id/plate-solving/hints` gives the hints an image would use, and `POST /api/plate-solving/:jobId/cancel` cancels.
- Images → Plate Solver (`web/src/images/PlateSolverPanel.tsx`, store `web/src/platesolving/platesolving.ts`) edits the document's request and sends it only with Solve Image; on a camera tab it edits the plate solving settings of the physical camera instead (`CameraSettings.plateSolving`, `effectivePlateSolveRequest`), which TPPA and the other operations of that camera apply, keeping only the hints in the document, so a typed position never reaches an operation; the request is editable before the document has an image (`imageUnavailableReason` says why), with Solve Image disabled until it has one. The solution shown is the latest submitted job of the image unless the operator chose another one or the header's (`ImagePlateSolvingState.selected`), so a job that ends never replaces a chosen solution; results are fetched only for the image shown. Zoom, pan, stretch, and the overlay toggles never solve.
- TPPA integration: `PlateSolvingService.solve(imageId, request, signal, origin)` resolves to the result of one image (a search without a solution completes with `outcome: noSolution`), runs with the manual priority, is never replaced by a newer frame, cancels with its signal, and throws `PlateSolvingError` with the job code otherwise; a preparation resolved once keeps the provider settings of a whole session. TPPA jobs carry the `tppa` origin (session, camera, frame id, and the pose during acquisition).
- Sync Mount (the Mount section of Images → Plate Solver, shown with a solution) syncs the MOUNT of the active equipment setup on the centre of the solution shown, after a confirmation, through `POST /api/connections/:id/mounts/:deviceId/sync`: the ICRS centre is sent as J2000 in decimal hours and degrees (`mountSyncTarget`). It is offered only while the mount is connected, can sync, is not parked, and no operation or command holds it (`mountSyncBlocker`); the server checks again. Nothing slews or centers the mount.
- Coordinates read from a solution are in its own frame: `wcsFrame` (`web/src/platesolving/wcs.ts`) names it `ICRS` or `FK5 J2000` from RADESYS, else EQUINOX, and every label shows it; the toolkit takes FK5 J2000 as the ICRS (within 0.03″) but the UI never relabels it. Separations and position angles (`skyOffset`) use the toolkit's atan2 formulas (`sphericalSeparation`, `sphericalPositionAngle`), from north through east, undefined for coincident or antipodal positions.
- Measurements and markers (`web/src/platesolving/measurement.ts`, state `ImageViewState.astrometry`, tool `web/src/images/astrometryTool.ts`) are kept per document as points in viewer pixels, kept inside the image, never as sky positions, in tab memory only: their values are computed again from the selected solution, so choosing another one keeps what was pointed at, and a point it cannot unproject makes them unavailable. A camera tab clears them when it shows another frame. A distance reports its great-circle separation, the position angle from north through east, ΔRA and ΔDec (a difference of right ascension, not an angle on the sky), the gnomonic east and north offsets of its end around its start, and its length in pixels, and is drawn along the great circle through the WCS. A rectangle is axis-aligned in image pixels, not in right ascension and declination: it reports the great-circle lengths of its four sides, of its two centre lines (between the midpoints of opposite sides), and of its diagonals, and its size in pixels, since one width would mislead under distortion. A circle has a constant angular radius on the sky around its centre, set by a rim point: its outline is that small circle sampled at every position angle (48 to 360 vertices, about one per 6 screen pixels) and projected through the WCS, so it may look elliptical, and it reports its radius, diameter, and centre; a degenerate or unprojectable one is unavailable. A marker is a fixed point with its coordinates in the WCS frame and its zero-based pixel. The measure mode of the viewer toolbar (per document, Pan by default, disabled without a solution or while Guiding picks a star) owns every press: a drag draws, or a click then a second click, and a click places a marker; with the Plate Solver tool shown, presses on a handle (12 px: the points of a distance or circle, the corners and edge midpoints of a rectangle) or a marker drag it in any mode and a click selects the item whose outline is under it, the rest pans. The gesture in progress lives in its own store, so drawing renders only its overlay; Escape drops it, then leaves the mode, then clears the selection, and Delete removes the selected item. The Measurements and Markers sections of the panel list them with their values, and rename, hide, delete, and clear them.
- The context menu of a solved image (`web/src/images/ImageMenu.tsx` over the generic `ContextMenu` of `web/src/ui/`, opened by a right click or a long press on a point inside the image; elsewhere the browser's own menu is kept) copies the point's right ascension and declination with the frame's name, or its zero-based pixel, adds a marker there, or starts a distance from it (Measure From Here); the drawing actions are disabled while Guiding picks a star. Every action uses the point the menu opened on. Copies go through `copyText` (`web/src/clipboard.ts`): the Clipboard API where the context is secure, otherwise a selection copied by the browser, since the app is usually opened over plain HTTP on the local network; a copy that fails keeps the menu open and says so.
- Target Offset (`web/src/images/TargetOffsetSection.tsx`, drawn by `web/src/images/TargetOffsetOverlay.tsx`, values `targetOffset` in `web/src/platesolving/measurement.ts`) is read only: it reports the offset of one target per document from the solved centre of the image (the separation, the position angle from north through east, and the east and north offsets on the plane tangent at the centre), and where the target falls in the image. The target is a marker of the image (located with the selected solution), a right ascension and declination typed in the frame of the solution, or the catalog star or deep-sky object selected in Sky, taken at its J2000 catalog position, epoch J2000.0, without proper motion; solar-system bodies, minor bodies, constellations, and the mount are refused with the reason. Inside the image the target is a ring with a dashed line from the centre; outside it, an arrow at the border along the direction towards it, labelled with the separation. Its values follow the selected solution; a marker target is dropped with its marker or when a camera tab shows another frame (which clears the markers), while a typed or Sky target is kept across frames. It never changes the Sky selection and nothing is sent to a mount.
- Limitations: only TAN and TAN-SIP solutions in the ICRS or FK5 J2000 are accepted; ASTAP may not write SIP terms; solve-field applies its own ±30% scale window and only nova takes `scaleTolerance`; ASTAP's "not enough stars" (exit code 2) is reported as a search without a solution.

## Image Processing Contract

- One service, `ImageProcessingService` (`api/src/imageprocessing.ts`), applies a pipeline to an image document: an ordered list of single-image operations of the toolkit (`ImageProcessingOperation`): debayer, automatic background extraction, background neutralization, arcsinh stretch, multiscale linear and median transforms, Gaussian blur, sharpen, cosmetic correction, horizontal and vertical flips, and grayscale. A request carries only the enabled steps, in order, each with the id the editor gave it; the job keeps them as an immutable snapshot. Parameters are the toolkit's own, which clamps them; they are not validated.
- What a pipeline can apply to an image is checked when it is submitted (`checkPipeline`), from the channels and trusted CFA pattern of the source, following what each step makes of them: debayer needs a mono image and a pattern (the trusted one for `auto`) and makes RGB, grayscale makes mono, background neutralization needs RGB, and a raw CFA mosaic takes only debayer, cosmetic correction (by colour phase), and the flips (which keep the pattern in phase). A refusal is `422 incompatibleImage` with the `stepId`; no operation is skipped or converted silently.
- The source is never changed: the image worker hands a full copy (`ImageStore.processingImage`, a trusted pattern named at the image origin) to a worker of its own (`api/src/imageprocessing.worker.ts`), which applies the steps in order, announcing each one, and transfers the result back. Only when every step succeeded is the result adopted as **one** derived document (`ImageStore.adopt`, provenance `processing`); a failure names its step (`errorStepId`, `processingFailed`), and a failed or cancelled job adopts nothing, even when the cancel arrives during the adoption.
- Scheduling uses the shared `AnalysisScheduler`: one pipeline at a time, at most 16 waiting, in arrival order, and at most one waiting or running pipeline per source image (a second one is `409 busy` with the job). A job retains its source until it ends. A running pipeline is cancelled, or stopped after 10 min (`timeout`), by terminating its worker. Results are never reused: running again creates another document. No device is held.
- Jobs are published as `imageProcessing:updated` (state, `currentStepIndex`, `completedSteps`, `outputImageId`, the failure), never with pixels or paths; `GET /api/image-processing` is the snapshot, `GET /api/image-processing/:jobId` one job, `POST /api/images/:id/processing` submits (202), and `POST /api/image-processing/:jobId/cancel` cancels.
- The output document of a completed job is handed to a client by `POST /api/image-processing/:jobId/claim`, which answers its `ImageInfo` (again for a repeated claim while it is open; `expired` once closed, `invalidState` before completion). A document never claimed within `CLAIM_GRACE` (10 min) is closed, so a tab that disappeared leaves no orphan; a claimed one follows the lifecycle of every document.
- Images → Image Processing (`web/src/images/ImageProcessingPanel.tsx`, `ProcessingStepCard.tsx`, `ProcessingStepForms.tsx`) edits the pipeline of the document (`ImageProcessingDraft` in its view state, so a camera tab keeps it across frames and a reconnection of its camera) as cards that are added from a grouped selector (`imageprocessing.catalog.ts`), reordered by dragging their handle or with Move and Alt+↑/↓, enabled or disabled (a disabled step keeps its parameters and is never sent), expanded independently of that, edited, duplicated (new id), and removed. Run Pipeline sends a deep copy of the enabled steps, so edits during a run apply to the next one; it is disabled, with the reason, without an image, without an enabled step, while a pipeline of the document runs, or when a step cannot apply (`pipelineIssue`, the same rules as `checkPipeline`), whose card shows why, as it shows a refusal or failure naming it. A camera tab runs on the frame it shows and keeps following the camera.
- The mirror (`web/src/images/imageprocessing.ts`, in `SERVER_STORES`) never lets a late event take a job back to an earlier state or fewer finished steps. A tab claims only the jobs it submitted, once, on the event or the snapshot that shows them completed (or on the answer of a submission whose job already completed); the output opens as an unsaved derived document, the active one only when its source still is. Stop Processing waits for the server to report the end.
- Limitations: no preview, no memory budget beyond the size of the image (a pipeline holds several copies of it while it runs); jobs do not survive a restart, and pipelines being edited do not survive a reload; the min-max rescale of the source read is kept, so a save writes the processed samples in the scale of the source; XISF stores the HISTORY of a derived image as one keyword.

## Auto Focus Contract

- `AutoFocusSessions` (`api/src/autofocus.ts`) runs the toolkit's `runAutoFocus` for one camera and one focuser inside a single `focuser.autofocus` operation, which holds both devices for the whole session; the runner nests its focuser lease and the per-frame camera leases in it. The runner owns the sampling, the fitting (Hyperbolic, Parabolic, Trend Lines, and the two combined modes), and the best position; nothing is fitted in `api` or `web`.
- The service supplies the runner with the backlash compensated mover of `FocuserCommands` (plus an optional settle wait), the `CameraCapturer` of the capture service (one FITS frame per position, written to a temporary directory and deleted after it was measured, never saved as a capture), and `StarDetectionService.measure`, whose median HFD of the accepted stars (Multi-Star) is each measurement. The provider and its ASTAP settings are fixed when the session starts; a failed detection is an invalid point of the curve, never a fallback to the other provider.
- The frames take the exposure time of the Auto Focus form (`AutoFocusSettings.exposureTime`) and the camera settings (gain, offset, binning, subframe, readout mode) of the physical camera, shared with Camera Acquisition (`CameraSettings.exposure` of the profile), whose exposure time is never sent, fitted to the camera's capabilities by `fitExposure` and snapshotted in the request, so editing them never changes a running session; the Auto Focus panel edits the exposure time and never the camera settings, which only Camera Acquisition does; the frames are measured with the profile's star detection request (see Star Detection Contract), the Auto Focus form holds the exposure time and the routine, and the frame type is always LIGHT. Every frame snoops the focuser of the session and the mount, filter wheel, and rotator of the equipment setup (`AutoFocusRequest.snoop`).
- After the runner moved the focuser to the best focus, one more frame there records the verified HFD, kept apart from the HFD the curve estimated; a session completes only after it. A rejected curve fails without a best focus, and the runner moves the focuser back to the start. A stop, or an Equipment Control stop of the focuser (which cancels the operation holding it), cancels where the session stands. When the request sets `restoreOnStop` (the form's default), a stop of `POST /api/autofocus/:sessionId/stop` then moves the focuser back to the start position in an operation of its own, once the session released it and only if it is free (`restoring`, then `cancelled` with `restored`); a second stop cancels that move where it stands, and an Equipment Control stop or a disconnection never moves the focuser back. While a frame is exposed, the summary carries the driver's countdown as `exposure` (microseconds and percent), cleared once the frame was read.
- Sessions live in memory: the latest of each camera, its measurements (requested and observed position, image id, HFD, star counts), and its curve, sampled from the runner's own regressions (`api/src/autofocus.curve.ts`). `autofocus:updated` events carry summaries; `GET /api/autofocus` and `GET /api/autofocus/:sessionId` are the snapshot and the complete record. Each frame is recorded in the capture frame registry as the latest frame of its camera (origin `autofocus`, frame id `sessionId:capture`, the verification numbered after the samples) before it is measured, and the registry closes it once a newer frame of the camera replaces it and no lease holds it; the measurement job retains the document until it ends. The service never closes frames itself, so a measurement's image id stays open only while it is the latest frame or leased.
- Limitations: focusers that only move relatively are refused; there is one frame per position and no repeated samples; the runner's sweep starts `initialOffsetSteps` steps out and comes back one step past the start before extending each side, so it is not symmetric; the filter wheel is never moved; the mount is not held, because the arbiter has no shared hold that would refuse GoTo and Nudge while letting tracking and guide pulses run, so a slew during a session goes unnoticed; sessions do not survive a restart. The simulated camera defocuses relative to its ±50000 step travel, so its curves need step sizes in the thousands.

## TPPA Contract

- `TppaSessions` (`api/src/tppa.ts`) runs the toolkit's `acquireThreePointPolarAlignment` and `refineThreePointPolarAlignment` for one camera and one mount inside a single `mount.tppa` operation, which holds both devices from the first frame until the session ends, refinement and pauses included, so no GoTo, nudge, capture, or Auto Focus can come between the poses or the refinement frames. The runner owns the RA motions, the acceptance of each pose, the geometry check (`core/src/observation/alignment/polaralignment.ts`), and the alignment; nothing is fitted in `api` or `web`.
- The operator chooses the RA direction (`WEST` or `EAST`), a slew-rate preset the mount announces (applied and confirmed by its echo before any motion), the RA rotation aimed at between poses (radians; the form keeps degrees, 6° to 15°), the settle delay, and the refinement delay. The motions are timed manual motions of the mount commander shared with Mount Nudge (`MountCommands.commander`): the first lasts 1 s, motions without measurable rotation grow fourfold up to 60 s, and once the mount rotated they are sized from the rotation observed per second; each one is stopped in a `finally`, and the stop waits for the mount to be quiescent, escalating to the abort. The rotation is measured from the solves (the change of hour angle about the celestial pole), never assumed from the motion time.
- A pose is accepted at 6° of rotation since the previous one, at most 30° from the first, with at least 1° of sky separation; a reversed motion, a declination change over 2°, a field within 10° of the pole (the first pose included, before any motion), a pier-side or tracking change, 12 captures without the pose, or an ill-conditioned triple fail the session as `unexpectedState`, never with an estimate. The seed pole error is about 2.4·σ/φ² for a solve error σ and a step φ, whatever the declination, which is why the limits are rotations.
- Frames take the exposure time of the TPPA form (`TppaSettings.exposureTime`) and the camera settings of the physical camera shared with Camera Acquisition (`CameraSettings.exposure`, whose exposure time is never sent), snapshotted in the request, as one LIGHT FITS frame each, with the mount snooped into the header; files are auxiliary, in a temporary directory deleted with the session. Each frame is recorded in the capture frame registry as the latest frame of its camera (origin `tppa`, frame id `sessionId:n`) before it is solved with `PlateSolvingService.solve` (origin `tppa`), whose provider and settings are resolved once when the session starts and never fall back to another. A frame without a solution is a warning: during acquisition the mount moves further, during refinement three in a row fail the session.
- After the third pose the session is `readyToRefine`. `POST /api/tppa/:sessionId/refinement/start` starts (or resumes) the refinement, which captures and solves every refinement delay and feeds `ThreePointPolarAlignment`, never commanding the mount; `…/refinement/stop` pauses it (`refinementPaused`), keeping the devices. A field that moved more than 5° on the sky between refinement frames means the mount slewed and fails the session. Every estimate carries the azimuth, altitude, and total errors and the knob changes inferred, and the overlay of its frame computed by `computeThreePointPolarAlignmentOverlay` with the center of the third pose as the persistent reference.
- `POST /api/tppa/:sessionId/stop` cancels the session wherever it stands (an Equipment Control stop of either device, or a disconnection, does too): `completed` once it had an estimate, `cancelled` before. When the operation ended, the preset it replaced is restored if the mount is free, reported as `slewRateRestored`, and, when the request sets `stopTracking`, the tracking it started is stopped, reported as `trackingStopped`, each with a warning when it could not be; with `stopTracking` false the tracking is left on.
- Sessions live in memory, the latest of each camera: `tppa:updated` events carry summaries with a monotonic `revision`; `GET /api/tppa` and `GET /api/tppa/:sessionId` are the snapshot and the complete record (poses, attempts, initial estimate, overlay). The start, `POST /api/connections/:id/cameras/:deviceId/tppa`, takes a token, so a repeated request answers the same session; it is refused with 422 when the solver is not configured or the mount is not equatorial, cannot move west-east or abort, lacks the preset, reports no site (0, 0), is parked, or is not tracking and cannot switch tracking. A mount that is not tracking but can switch it has its tracking started inside the operation before the first frame (`trackingStarted`). While a frame is exposed, the summary carries the driver's countdown as `exposure` (microseconds and percent), cleared once the frame is solved, through the `captureListener` the toolkit runner gives to every auxiliary capture (`exposureProgressListener` of `api/src/captures.ts`).
- Limitations: the backend knows no obstacle, cable, or mechanical limit the driver does not report, so the direction is the operator's responsibility; guiding or dithering by another program during the refinement goes unnoticed; refraction uses the default atmosphere; only the mount is snooped into the frames; sessions do not survive a restart.

## DARV Contract

- `DarvSessions` (`api/src/darv.ts`) runs drift alignment for one camera and one mount as a session of measurements. Each measurement is its own `mount.darv` operation, which holds both devices only while the toolkit's `runDarv` (`core/src/observation/alignment/darv.runner.ts`) exposes one frame, so the operator turns the knobs between measurements with the devices free. The runner owns the slew rate, the timing, and the motions; nothing is timed in `api` or `web`, and nothing is plate solved.
- The operator chooses the axis being adjusted (`azimuth` or `altitude`, which only tells where to point), the direction of the first RA motion (`EAST` or `WEST`), a slew-rate preset the mount announces (applied and confirmed by its echo before the exposure), and the leg duration (the form keeps 5 s to 600 s). The exposure is `darvExposureTime`: both legs plus a 3 s lead with the stars still, a 3 s turn budget, and a 3 s trailing margin. Once the exposure is seen Busy the runner waits the lead, moves out for the leg duration, stops, moves back for the same time, and stops; each motion is a manual motion of the commander shared with Mount Nudge, stopped in a `finally` that waits for the mount to be quiescent. A return motion that ended later than the earliest possible end of the shutter (dispatch plus exposure) fails the measurement instead of keeping a truncated trail; a mount that disconnects or stops tracking between legs fails it too.
- The timing measured on the monotonic clock shared with the capturer (lead, outbound, turn, return, trailing, adding up to the exposure) is kept with the measurement and given to the analysis, which excludes the stationary lead and trail from the drift baseline.
- The frame takes the camera settings shared with Camera Acquisition (`CameraSettings.exposure`) without its exposure time, as one LIGHT FITS frame with the mount snooped into the header; the file is auxiliary, in a temporary directory deleted with the measurement. The frame is recorded in the capture frame registry as the latest frame of its camera (origin `darv`, frame id `sessionId:generation`) before the devices are released.
- A measurement starts the tracking of a mount that is not tracking inside its operation, before the runner, and the session records it (`trackingStarted`); the tracking stays on between measurements, and an open session replaced on the same mount hands it to the new one. `POST /api/darv/:sessionId/finish` takes `{ stopTracking }` (the panel's "Stop the tracking when finishing" checkbox, on by default) and, when set, stops that tracking before the session is published as finished, if the mount is free (`trackingStopped`); a repeat or another finish meanwhile is refused with 409. Once the operation of a measurement ended, the preset it replaced is restored if the mount is free (`slewRateRestored`), and the frame, retained in the image store, is analyzed by `DarvAnalyzer` (`api/src/darv.analysis.ts`): `analyzeDarvImage` on a worker of its own (`api/src/darv.worker.ts`, embedded by `app/build.ts`), one analysis at a time, cancelled by terminating the worker. There is no sky transform, so the drift is the unsigned separation rate of the legs across the RA direction, in pixels per second, never a polar error. The outcome is `measured` (a drift from unclipped, resolved trails), `limited` (only clipped, saturated, or unresolved trails; no drift is published, never a zero), or `inconclusive` (no pair of legs), with the toolkit's diagnostics and a fit quality that is not a probability. Drifts are comparable only between measurements of equal settings.
- Measurement states: `preparing`, `exposing`, `outbound`, `reversing`, `inbound`, `finishing`, `analyzing`, then `ready`, `failed`, or `aborted`; `ready` says the measurement ended, not that the mount is aligned. Session states: `measuring`, `idle`, `finished`.
- `POST /api/connections/:id/cameras/:deviceId/darv` starts a session and its first measurement (replacing an idle or finished session of the camera), `POST /api/darv/:sessionId/measurements` repeats one with new settings, `POST /api/darv/:sessionId/abort` aborts the measurement wherever it stands (stopping the mount and discarding the exposure, or cancelling the analysis; an Equipment Control stop or a disconnection aborts it too), and `POST /api/darv/:sessionId/finish` finishes an idle session. Starts take a token, so a repeated request answers the same measurement; they are refused with 422 when the mount is not equatorial, cannot move west-east or abort, lacks the preset, is parked, is not tracking and cannot switch tracking, or tracks at another rate than sidereal, and with 409 while the camera's session measures or a device is held.
- Sessions live in memory, the latest of each camera, with the latest 50 measurements: `darv:updated` events carry summaries with a monotonic `revision`; `GET /api/darv` and `GET /api/darv/:sessionId` are the snapshot and the complete record (the paired trails of each analyzed measurement, in 0-based pixels).
- Limitations: with equal legs the order of the outer ends is not known, so the drift has no sign and does not say which way to turn a knob; the backend knows no obstacle or cable limit, so the direction is the operator's responsibility; a measurement runs at a slew-rate preset, not at the guide rate; the simulator's slowest preset (0.5°/s) is too fast to show a polar error within a test, so the analysis of real divergence is tested in `core`; sessions do not survive a restart.

## Flat Wizard Contract

- `FlatWizardSessions` (`api/src/flatwizard.ts`) acquires FLAT frames for one camera, filter group after filter group, as one `camera.flatWizard` operation holding the camera, and the assigned filter wheel and flat panel when the request names them, from start to end, including while it waits for the operator. Each filter group searches its exposure with trial frames, freezes it, then takes final frames until its count of accepted frames was published. The light stays constant within a group: there is no automatic brightness search, sky flat, dust cover, master, or calibration.
- Every exposure goes through the shared `CameraCapturer` with the camera settings of the request (`FlatWizardCaptureSettings`: gain, offset, binning, subframe, readout mode), frame type FLAT, FITS transfer, and the assigned wheel snooped into the header, written to a staging directory `.flatwizard-<sessionId>` inside the output directory (`directory`, or the default captures directory). Frames are measured by `FlatWizardAnalyzer` (`api/src/flatwizard.analysis.ts`) on a worker of its own (`api/src/flatwizard.worker.ts`, embedded by `app/build.ts`), which reads the file in the digital numbers of its source (`sampleScale: 'digital'`), never through the normalized documents of the image store, and returns the toolkit's single-frame analysis without maps and, for a final frame, its temporal sample (`measureFlatSequenceFrame`) instead of the decoded image.
- Each filter group names a 0-based filter `slot`. The filter is named by the name the wheel reports for that slot, or `Filter <slot + 1>` when it reports none or there is no wheel (`filterName`), resolved once when the session starts (`FlatWizardFilterRun.name`); that name goes into the file names, the frame context, and every message. The filter is selected by moving the wheel to the slot (confirmed by the wheel's reported position), or, without a wheel, by the operator, who puts the filter of that slot in place. The light comes from the panel at the group's `brightness` (driver units; absent keeps the reported one) and switched on, both confirmed by the panel's reported state, then `settleTime` seconds when something changed; without a panel the operator readies the light. A manual step publishes `pending` with a fresh `stepId` (`waitingForFilter`, which also covers a manual light, or `waitingForIllumination`), and only `POST /api/flat-wizard/:sessionId/continue` with that `stepId` resumes it; a stale or repeated confirmation is refused with 409 `staleStep`, and nothing else (tab, tool, profile, reconnection) confirms a step.
- Levels are observed DN with an unknown pedestal. The plane driving the exposure is the brightest plane of the first usable trial; only it is held to the group's `targetRange`, while every plane is checked for clipping and non-finite samples. A trial is `usable`, `clipped` (no observation; the exposure halves, and a clip at the minimum exposure fails), or `noSignal` (fails). An out-of-target first observation is followed by a second distinct exposure (twice or half, within the bounds), never a proportional guess; then `estimateFlatExposure` interpolates or fits an affine response. The search fails with an explanation when the target needs an exposure outside the bounds, the estimate is invalid, it would repeat an exposure, or `maximumTrials` is exceeded. Trial files are deleted after measurement and never published.
- A final frame is `accepted` when its target and finite-sample checks pass and clipping is not present, even when its absence cannot be proven without `effectiveClip` (the frame then carries `effectiveClipUnknown`); `rejected` when a check fails; `inconclusive` otherwise. An accepted frame is published under `{date}_{time}_{camera}_FLAT_{filter}_{seq}.fit` by a hard link of its original bytes (an exclusive copy where links are unsupported), never replacing an existing file; a rejected or inconclusive one is deleted. More than `maximumRejections` rejected or inconclusive frames, or a failed publication, fail the session; published frames always stay.
- Once a group has its frames, `finalizeFlatSequence` evaluates their temporal stability from the retained samples (outliers at 5 robust sigmas); fewer than three frames, or frames the toolkit refuses as one stack, are `notEvaluated`. The result only describes the acquisition: no frame is deleted, replaced, or modified for it.
- An assigned dust cover (`cover`, refused with 422 when it cannot open and close) is closed before the first frame (`closingCover`, confirmed by its reported state) and held for the whole session. A cover already closed when the session starts stays closed afterwards; one the session closed, or began to close, is opened again once the session ended, however it ended, after the light was switched off.
- A light the session switched on is switched off after the operation ended, with the panel taken again if it is free; otherwise, and likewise for a cover that cannot be opened again, `cleanupWarning` says what was left. Stopping (`POST /api/flat-wizard/:sessionId/stop`) cancels the operation at once, like the other camera operations: the exposure in flight is aborted and lost, a measurement or a manual step is abandoned, and the request resolves after the devices were released and the light cleanup ran. A disconnection of a held device cancels the session the same way, and the arbiter refuses captures, other camera operations, wheel moves, and panel commands on the held devices meanwhile.
- Session states: `preparing`, `closingCover`, `waitingForFilter`, `movingFilter`, `waitingForIllumination`, `settingLight`, `settling`, `exposing`, `measuring`, `saving`, `assessingSequence`, `stopping`, then `completed`, `cancelled`, or `failed`; filter groups go `pending`, `calibrating`, `acquiring`, then `completed`, `failed`, or `cancelled`, with their counts of trials, accepted, rejected, inconclusive, and failed publications.
- `POST /api/connections/:id/cameras/:deviceId/flat-wizard` starts a session (202 with `sessionId` and `operationId`; a repeated token answers the same session), refused with 404 for an unknown camera, wheel, or panel and 409 when one is disconnected or held, or the camera's session is running. Sessions live in memory, the latest of each camera: `flatWizard:updated` events carry summaries with a monotonic `revision`, the latest exposure, and, while a frame is exposed, its progress as the driver reports it (`exposure`: elapsed and remaining microseconds and percent, cleared once the frame was read); `GET /api/flat-wizard` and `GET /api/flat-wizard/:sessionId` are the snapshot and the complete record with the latest 200 exposures. File names are published without their directory.
- Every frame is also decoded from its staging file into the image store and recorded in the capture frame registry as the latest frame of its camera (origin `flatWizard`, frame id `sessionId:generation`, the `frameId` of its exposure in the session), so the camera tab shows it; an accepted frame is then recorded under its published file among the saved frames, which survive a restart, while trial and rejected frames stay previewed only. A frame that cannot be decoded is reported as `previewError` and never fails the session.
- Limitations: without a wheel, the filter name only names the files and the session; it is not written into the FITS header; sessions do not survive a restart.

## Guiding Contract

- `GuidingSessions` (`api/src/guiding.ts`) runs native guiding, without any PHD2 process, for one guide camera and one guide output at a time per camera: one toolkit `InteractiveGuidingSession` (`core/src/observation/guiding/session.interactive.ts`) over a `GuiderClient` of its own, from the first looped exposure until the stop route or the loss of a device. The toolkit owns the states, the tracking, the calibration, the controller, the pulse admission and the settle; the service only forwards commands, publishes the snapshot, the native events and the telemetry, and previews the frames. The guide camera and the guide output come from the request as exact device ids; changing roles or profiles never touches a running session.
- Resources: the session's root holds the guide camera for the whole session, published as a `camera.guiding` operation; while guiding (from Start Guiding until Stop Guiding, the stop, or the loss), its child run holds the physical device behind the guide output (the mount or the camera of its ST4 port) and its logical lifecycle resource, published as `guideOutput.guiding`. Every pulse goes through `GuideOutputCommander.dispatch` under that run (the commander of `GuideOutputCommands`), so ending the run waits for the observed end of every pulse and leaves the device blocked with the `guidePulse` cause when that end cannot be observed. While only looping, manual pulses, nudges and slews of the mount stay possible; the camera stays held. Losing the guide camera or the guide output ends the session as lost (`failure.reason` `disconnected` or `removed`); a reconnected device needs a new session.
- Frames: each guide BLOB is decoded on a worker thread of the session (`api/src/guiding.worker.ts`, bundled as an extra entry point of the executable), which takes the grayscale copy (`luminanceImage` of `api/src/imagedecode.ts`, shared with the image worker), detects its stars with the toolkit detector and the built-in settings of the request and samples their peaks (while the run holds the guide output and the previous frame was measured, only in squares of `GUIDING_REGION_RADIUS` (24 px) around the measured star, the lock, and the `GUIDING_REGION_STARS` (16) accepted stars of highest SNR, padded for the detector and merged where they overlap (`api/src/guideregions.ts`), keeping only detections from the tracker's minimum SNR, since the frame quality the guider gates on is the accepted fraction of the detections and the noise peaks of the crops would otherwise sink it, about 30 ms instead of 500 ms on a 1280 × 1024 frame; looping, selecting, a lost frame, and ASTAP use the whole frame), and answers the image, the stars and the FITS/XISF bytes; the tracker reads the stars synchronously. A session whose detector is ASTAP has the worker decode only and runs ASTAP's extraction on the frame's FITS file in a temporary directory of the session, removed at its end, about half a second per frame, sampling the peaks on the grayscale copy; a run in flight is killed by the end of the session. The bytes of the newest frame are opened as a capture document and recorded as the latest frame of the camera (origin `guiding`, never saved); only the newest frame waits while another one is opened, so the preview never holds the guiding back. `guiding:frame` names the frame's `imageId` with its overlay (lock and search positions, search square, measurement, primary star, detected and accepted stars with their HFD), in pixels of the full decoded frame from its top-left; it is sent before the frame becomes the latest of the camera, so a tab has the overlay when it switches to it, and the tab keeps the overlay of the frame before until then, so the markers never blink.
- `POST /api/connections/:id/cameras/:deviceId/guiding` starts a session (`GuidingStartRequest`: the guide output, the exposure in ms, the camera settings sent once, the tracking mode, optional optics, calibration and controller overrides passed to the toolkit unchanged, the guider client settings (`GuidingClientSettings`: dither pattern, search square side in pixels clamped to [16, 128], sticky lock position, whether the RA return of a calibration and a dither are followed by a fast recenter (PHD2's, on by default in the toolkit), and whether a meridian flip of the calibration reverses the DEC output, which no route triggers yet), the devices snooped into the guide frame headers, set once when the session starts, and the star detector with its settings, the built-in defaults when absent); 202 with `sessionId` and `operationId`, and a repeated token answers the same session; 404 for an unknown camera or guide output, 409 when one is disconnected or the camera is held, 422 when the guide output cannot pulse guide or the detector is ASTAP while it is not configured.
- Durable commands answer 202 with a `commandId` once accepted (a repeated token answers the same command) and report their outcome as the `command` of the session record: `POST /api/guiding/:sessionId/start` (recalibrate, settle), `/stop-guiding`, `/pause` (`corrections` keeps exposing, `all` stops the exposures; a pause during calibration is always full and its resume calibrates again), `/resume` (settle), and `/dither` (amount in guide pixels or radians, RA only, guided settle; as in PHD2 the toolkit moves the lock from where it is, reflects an offset that would take it out of the frame, clears the controllers, and, with fast recenter, moves the star straight to the new lock in steps of at most 0.7 of the search half-side before the corrections resume). Immediate commands answer 200 or 204, or the failure of the toolkit: `/target` (a pixel of the current frame, or the best star of the whole frame, even when one is already selected), `/target/clear` and `/calibration/clear` (422 while guiding), and `/exposure` (ms). `POST /api/guiding/:sessionId/stop` ends the session once the guide camera and output were released (204), or answers the failure when the end of a pulse could not be observed. Commands of an ended or unknown session answer 404.
- `GET /api/guiding` lists the latest session of each guide camera; `GET /api/guiding/:sessionId` is its record (`GuidingSessionSummary`: the snapshot, the guide exposure, the solved calibration with its rates in pixels per ms and angles in radians, the progress of a running calibration (`calibrating`, from the diagnostics of each `calibrationStep`: the phase, and per leg the steps against their limit and the travel in pixels against what it needs, RA `minNetRaTravelPx`, the return within `maxClearingOffsetPx`, DEC `minNetDecTravelPx`, and, when the calibration returns along DEC once solved as PHD2's south leg (the toolkit default), the DEC return steps with the distance to the start, with the backlash so far and the unusable frames, cleared once the guider leaves `calibrating`), the RMS of the latest `GUIDING_RMS_WINDOW` (50) measured guide steps in guide pixels, the pixel scale in arcsec per pixel when the optics are known, the progress of the guide exposure the camera counts down (`exposureProgress`, microseconds and percent, from the camera's exposure countdown while it exposes), the Star Profile of the guide star of the latest measured frame (`star`: the toolkit's `measureStarProfile` at the measurement on the grayscale copy, with its horizontal and vertical cuts of ±12 px less the background, `api/src/guidingprofile.ts`; intensities normalized, `adu` converting them), the latest frame and command, the latest event sequence and telemetry cursor, and a revision). `GET /api/guiding/:sessionId/events?after=` and `/telemetry?after=` page the control events (every native event except the per-frame ones, at most 500) and the telemetry samples (one per guide step or lost frame, at most 2000), with `truncated` when the requested position was already forgotten. Events: `guiding:updated` (the record), `guiding:event` (one control event and its sequence), `guiding:telemetry` (one sample and its cursor), and `guiding:frame`. A tab that reconnects reads the record, then the events and telemetry after the positions it has.
- The web store `web/src/camera/guiding.ts` (`guidingRuntime`, in `SERVER_STORES`) mirrors the latest session of each guide camera from `guiding:updated` and the snapshot, ordered by revision, and keeps the control events and telemetry of those sessions only (at most as many as the server), appending each one at its position and filling any gap, or a reconnection, from the pages after the last position it has; a truncated page replaces what it had. `guiding:frame` keeps the newest frame of each session with its overlay; there is no route for the overlay of an earlier frame, so a reload shows it from the next frame. `guidingRequest` builds the start from the profile's guiding form, sending exposures in ms.
- Limitations: the controller and tracking settings are fixed when the session starts (only the exposure changes on a running session); the calibration is kept only within a session and the toolkit does not compensate the declination, so a new Start Guiding after a slew should recalibrate; a target pixel is not checked against the frame the tab shows; sessions, events, and telemetry live in memory and do not survive a restart.

## Mount Pointing Model Contract

- A model maps the coordinates a mount was commanded to onto the sky position it reached. The fit, the prediction, and the inverse correction are the toolkit's (`core/src/observation/mount/pointing.ts`); nothing is fitted in `api` or `web` by other means.
- Frame (`api/src/mountpointing.frames.ts`): a sample holds the exact JNOW values the driver received, as opaque coordinates of the driver, and the plate solved ICRS center reduced to the true apparent topocentric place of the middle of the exposure, without refraction (`apparentFromIcrs`). Refraction, the semantics of the driver, and the mechanics of the mount therefore end up in the fit. The reduction is not the mount commander's `equatorialFromJ2000`, which leaves aberration out, so a model of that frame would carry up to about 20″ that drift over the year. The error is solved minus command, east and north positive.
- Fitting (`api/src/mountpointing.fit.ts`, `mountpointing.worker.ts`, embedded by `app/build.ts`) runs on a worker of its own, one fit at a time, since the leave-one-out refits take seconds at the sample counts of a run. Samples cross as plain numbers, because a toolkit `Time` cannot be cloned. Cross terms are off by default, because at one site `sinAlt` is an exact combination of `sinDec` and `cosHA·cosDec`, which leaves the default features singular from about 65 samples on; pier terms are used only when the training samples hold both sides.
- Withheld samples never enter a fit. They measure it on sky it has not seen, and the offline gate of a revision (`unusable`, `failed`, `passed`) requires a usable model, at least 6 of them, a withheld RMS under 80% of their RMS before correction, and one on each pier side trained. These limits are provisional until simulator and real-mount runs justify them. A measure a fit cannot give is absent, never zero.
- Persistence (`api/src/mountpointing.store.ts`): one versioned file per model, holding its samples and revisions, read once on first use. A corrupt file, or one of a newer version, is listed as `unavailable`, never overwritten, and costs only itself. Samples and revisions are immutable, saves of a model run one at a time, and a save from an outdated revision is refused with its current state. An acquisition found `running` or `paused` is `interrupted`: nothing resumes by itself. A file never says a model is active. An export holds the samples, the plan, and how the latest revision was fitted, never coefficients or a verdict, so an import is fitted and judged again here, and only its version is checked.

- Model library (`api/src/mountpointing.ts`, mirror `web/src/mountpointing/mountpointing.ts`, in `SERVER_STORES`): `GET /api/mount-pointing/models` lists the summaries, the unavailable files, and the fits; `GET …/:modelId` is the complete record, loaded on demand; `POST` imports an exchange document; `PATCH` renames; `DELETE` removes; `GET …/:modelId/export` downloads; `POST …/:modelId/fit` answers 202 and adds a revision when the worker ends. Every edit carries `expectedRevision`, and an outdated one is `409 conflict` with the current summary. There is no draft on the server: a draft is the form of a tab until it asks for a fit, and an exclusion is a choice of that fit, so it never changes a sample or an earlier revision. A model a session or an activation holds can be neither fitted nor removed (`409 busy`). Events carry a sequence per process, and the mirror drops older ones and leaves what an event changed during a refresh.

- Acquisition (`api/src/mountpointing.sessions.ts`): `MountPointingSessions` walks the waypoints of a plan (`planPointingWaypoints`, fixed on the local sky as hour angle and declination, leaving 10° around the poles free), computing the right ascension of each one from the sidereal time of its dispatch. Each waypoint is an uncorrected GoTo through the commander under the session's own lease, with `tolerance: 0` so the commander never skips it, and never a Sync; a settle wait; one temporary LIGHT frame, recorded as the latest frame of the camera (origin `mountPointing`) and deleted once solved; and one solve around the J2000 place of the command, with the solver settings resolved for each stretch of work and no hint typed for an image. The pier side recorded is the one the mount reported. A frame without a solution is exposed again once, without a slew; a waypoint without a solution, or whose solution is more than 5° from the command or differs in scale by more than 5% (provisional) from the session's median, is a rejected sample, kept with its reason and out of every fit. Solvers report no quality, so `uncertainty` is never set. Five waypoints in a row without a sample pause the session. A sample is saved before anything moves again.
- Each stretch of work is one `mount.pointingModel` operation holding the camera and the mount. `POST …/pause` and `…/stop` answer 202 at once, since a camera may stay held up to `FRAME_TRANSFER_TIMEOUT`, and cancel it, losing the exposure in progress. `…/resume` is a new operation with a token, after the mount, its site, and its state are checked again. An operation that ended with a mount that is not quiescent leaves the session `blocked`, because a failed stop shows only in text: a resume is refused until the session is stopped. A cancel from outside (an Equipment Control stop) or a failure pauses the session with the reason. A camera has one session that has not ended; a session owns its model until it ends. An interrupted or stopped model is continued by starting a session with its `modelId`, refused for another mount or site, which visits what it misses.
- Admission (`422`): the plate solver configured, a site reported, not parked, `canGoTo`, `canAbort`, tracking or able to track (started inside the operation and stopped at the end unless the request keeps it), not `ALTAZ`, and `UNKNOWN` only with the operator's confirmation, since nothing can prove a mount is equatorial otherwise.
- A run with at least 12 training samples is fitted by itself with Auto when it ends. Limitations: the backend knows no obstacle or cable limit the driver does not report, so the sky is the operator's responsibility; sessions do not survive a restart, and their model then reads `interrupted`.

- Images → Pointing Model Builder (`web/src/camera/PointingModelBuilderPanel.tsx`, a camera operation of camera tabs only) acquires samples and never touches a model. It requires the camera to be the Main Camera of the setup, so a model belongs to one optical train, and takes the MOUNT of the setup. The exposure time is its own form's; the other camera settings are shown and belong to Camera Acquisition, and the solver is shown and belongs to Images → Plate Solver, each with a link that only selects the tool on the same tab. Preview Plan asks `POST /api/mount-pointing/plan`; Start asks for confirmation that the mount is clear to move. The mirror (`mountPointingRuntime`) follows sessions by camera, by revision, leaving what an event changed during a refresh.

## Notifications Contract

- Notifications are facts about operations, never their state: `NotificationService` (`api/src/notifications.ts`) receives every event the composition publishes for the connections, operations, and sessions (`publish` in `api/src/index.ts` broadcasts the event first, then hands it over) and keeps only what `NotificationClassifier` (`api/src/notifications.rules.ts`) asks for. Its own `notification:created` events are broadcast directly, never classified again. Classifying, storing, and publishing never throw into or wait inside the publishing service.
- Classified transitions: lost connections (`connection:close` with cause `lost`, warning); completed or failed captures, Auto Focus runs, and Flat Wizard runs (success or error); TPPA ready to refine (info) or failed; each new Flat Wizard manual step, by `stepId` (warning), and its cleanup warning; guiding calibrations completed and sessions ended by a failure; failed DARV measurements, by generation; failures of the long-running device commands (go to, slew, flip, park, unpark, home, focuser, wheel, and rotator moves, cover and dome commands). Quiet: progress, telemetry, frames, device events, successful operations, session operations (reported by their sessions), manual moves, pulses, property writes, every `aborted` failure, and the `removed` or `disconnected` failures of a connection closed on request, until it opens again.
- Each record (`NotificationRecord`: id, sequence, creation instant, level, stable code, title, message, source with the connection endpoint, optional target) is created once per occurrence key, also across restarts. Text comes from fixed templates, device names, and fixed descriptions of the failure reasons; driver errors, paths, and payloads are never copied. Targets are typed (`cameraTool` with the camera tab tool, or `equipment`), never URLs or commands.
- History: at most 500 records for 30 days in `~/Nebulosa/notifications.json`, written atomically one write at a time with the changes made meanwhile coalesced; a crash can lose the write in progress, and a newer file version is never overwritten. `GET /api/notifications` answers the whole retained history, newest first; there is no write route.
- Web: `notificationsState` (`web/src/notifications/notifications.ts`, in `SERVER_STORES`) mirrors the events and refetches the history on every socket open, keeping the events received during the request. Only notifications arriving live after the first fetch become toasts (`NotificationToasts`, mounted once by the shell; at most 3, success for 2 s, warning for 4 s, error for 5 s; info never). The same host shows a toast of the tab itself when its event socket stays closed for 5 s after it was open (`onClose` of `web/src/events.ts`, `NotificationsState.server`), then a short reconnected toast when it reopens; the server cannot report its own loss, so this toast never enters the history. Read and dismissed states belong to the active profile (version 13).
- Scope: the bell counts and the panel lists the notifications of the active profile's saved connection, matched by endpoint so they still count after it closed, plus application-wide ones; the panel can show every connection. Choosing a notification marks it read and opens its target only when it is open now (`web/src/notifications/target.ts`: the camera tab of that camera, or the device of the watched connection); it never switches profile or connection, commands a device, or touches a session.
- Limitations: no browser, sound, or remote delivery; read states are not synchronized between browsers; a camera tab shows only the latest session of its camera, so an older session is not reopened.

## Capture–Sequencer Compatibility Report

- There is no sequencer engine to integrate. It will be an `api` service composed of the same services Capture uses: capture via `CameraCapturer`, filter, focus, dither, and mount commands through the commanders, all under the `OperationRegistry`.
- Acquisition exists once, in `CameraCapturer`. Camera Acquisition, Auto Focus, DARV, TPPA, and Flat Wizard must call the same `api` capture service, never their own exposure loops.
- Every acquisition snoops the managed devices of the equipment setup (mount, focuser, filter wheel, rotator; `captureSnoop` in `web/src/camera/capture.ts`) into the frame headers; from an Images camera tab only when its camera has a role in the setup (`CameraOperationContext.snoop`). Requests name them by device id on the camera's connection (`CaptureSnoop`), and `api` resolves the ids to the driver names (`snoopedDevices`); snooped devices are read, never acquired.
- The Camera Simulator of the `SIMULATOR` connection (`api/src/connection.ts`) reads the devices a capture snoops through the shared managers, and starts on the `SKY` catalog source: the J2000 stars of the sky catalog around the mount's pointing (`catalogStars` in `api/src/sky/catalog.ts`, `skyStarSource`), through a 50 mm f/2 lens so the magnitude-8 catalog fills its 7.6° × 6.1° field with enough stars to plate solve. The Guide Camera Simulator renders the same sky through a 40 mm lens with a 2 s noise reference exposure, and the Camera Simulator with 3 s (`noiseExposureTime`, 60 s in the toolkit), since star fluxes scale with the exposure over that reference and exposures of seconds would otherwise show no star above the noise. Proper motion is not applied.
- A run resolves its connection and device ids when it starts and keeps them. Changing the active profile in a tab never redirects it.
- The UI observes a run through snapshots and events, never by owning it.

Browser storage goes through `web/src/storage.ts` (and `MemoryStorage` in tests); server files are written atomically, synced to the disk before the rename so a power loss leaves either the previous content or the new one, and refuse to overwrite a file of a newer version. SIGINT, SIGTERM, and SIGHUP end the process (`app/src/main.ts`) only after `flushStores` of `api/src/index.ts` wrote the pending changes of the capture frames and the notifications; a second signal ends it at once.

Profile format changes add a version (`PROFILES_VERSION` in `web/src/profile/schema.ts`) and a case in `migrate` (`web/src/profile/migrate.ts`); older documents are read, and newer ones are never overwritten.

Camera forms belong to the physical camera, never to a camera role: `ProfileSettings.cameras` keeps, per saved connection id and device id (`CameraIdentity`, `profileCamera`), the exposure time of Camera Acquisition and the camera settings its other operations share (`exposure`), the rest of the Camera Acquisition form (`acquisition`: mode, count, delay, frame type, output), the Auto Focus form (`autoFocus`, with its exposure time in seconds and `restoreOnStop`), and the Pointing Model Builder form (`pointingModel`: exposure time in seconds, pattern, number of points, minimum altitude and meridian avoidance in degrees, settle delay, whether the end stops the tracking the session started; version 16), the TPPA form (`tppa`: exposure time in seconds, RA direction, slew-rate preset name, rotation in degrees, settle and refinement delays, whether the end stops the tracking the session started; version 5), the DARV form (`darv`: axis, direction of the first motion, slew-rate preset name, leg duration in seconds, whether the finish stops the tracking the session started; version 6), and the Flat Wizard form (`flatWizard`: filter groups with exposures in seconds, DN targets, wheel slots, and panel brightness, the directory, effective clipping level in DN, settle time, and limits; version 7), and the guiding form (`guiding`: guide exposure in seconds, tracking mode, star search square in pixels and sticky lock, whether Start Guiding recalibrates, calibration pulse and correction ceilings in ms, RA and DEC gains, the settle in guide pixels and seconds, and the dither size in guide pixels, RA-only, pattern, and fast recenter (on unless saved off), and whether a meridian flip reverses the DEC output; version 8, whose guide frames take the camera settings of the camera's `exposure` without its exposure time). Version 9 moves the guide focal length in mm that the version 8 guiding forms held to the profile's guide telescope (`guideTelescope`, the optics of Equipment Setup beside the telescope), taken from the form of the active setup's Guide Camera, else the first form with one. An operation fits them to the camera when it starts and keeps that snapshot. An Auto Focus or TPPA form saved before it held an exposure time takes the one of the camera's `exposure`, which it was using. Version 4 moved the forms that version 3 and earlier kept per camera role (`CaptureSettings.acquisition`, `autoFocus`) to the camera each equipment setup assigned that role, dropping the forms of roles without a camera and the post-capture analysis and plate solving settings; the Capture workspace preferences (`capture`), removed with that workspace, are ignored when read. A camera of a profile without a saved connection shows the defaults and keeps nothing.

Mount Remote Control bindings belong to the physical mount: `ProfileSettings.mountRemoteControl` (version 10) keeps, per saved connection id, mount id, and protocol, the host and port a listener was last started with (`mountRemoteBinding`, `setMountRemoteBinding`), `DEFAULT_MOUNT_REMOTE_BINDINGS` before that. They are preferences only: a running listener lives in `api` memory and is never started, stopped, or rebound by a profile.

The display settings applied last in Images (version 11) are kept per physical camera, in its `display` form of `ProfileSettings.cameras`, for the frames of its camera tab, and globally in `ProfileSettings.imageDisplay` for every file and derived document (`imageDisplaySettings`, `setImageDisplaySettings`, read and written through `ImagesIo.loadDisplay` and `saveDisplay`). Only settings a rendering applied are saved, never a popup draft; a camera of another connection than the watched one saves none.

The streak detector settings of Images (version 12) are kept in `ProfileSettings.streakDetection`, every field restored within the toolkit's range and the orientation tolerance within the voting budget of the angle step; the context jobs of a detection are never stored.

The notifications a profile read or dismissed (version 13) are kept in `ProfileSettings.notifications` as lists of notification ids (`markNotificationsRead`, `dismissNotification`), since the server keeps one history for every browser and never stores read states. Each refresh of the history drops from every profile the ids the server no longer retains (`pruneNotificationPreferences`), so each list holds at most the 500 retained ids; read states are never synchronized between browsers.

Version 14 stored an observatory code for the solar-system searches of Images → Annotation (`annotation`), removed since: the searches use the site of the image header. A stored code is ignored when read, and the version stays 14.

The plate solving settings of a camera (version 16) are kept in its `plateSolving` form of `ProfileSettings.cameras` (`cameraPlateSolving`, `setCameraPlateSolving`, defaults `DEFAULT_CAMERA_PLATE_SOLVING`): provider, strategy, downsampling, and scale tolerance, never hints. Images → Plate Solver edits them on the camera's tab, and the panels of the operations that solve its frames only show them (`CameraPlateSolvingSection`). Version 16 moved them from the TPPA form (`tppa.solver`), which kept no scale tolerance.

The appearance of the astrometric aids of solved images (version 15) is kept in `ProfileSettings.imageAstrometry` (`imageAstrometrySettings`, `setImageAstrometrySettings`, defaults `DEFAULT_IMAGE_ASTROMETRY` of `web/src/platesolving/preferences.ts`): the coordinate format and decimals, the grid labels, minor lines, opacity (0.15–1), and color (a theme color, or red right ascension and blue declination), the crosshair, the scale bar, and the orientation mode, each invalid field restored to its default. Whether a document shows its centre and grid stays in its view state, in tab memory, off by default for the grid.

## Test Baseline

Run before every delivery. CI (`.github/workflows/test.yml`) installs with `--frozen-lockfile`, writes an empty catalog with `bun make:catalog --empty` and placeholder Moon assets with `bun make:moon --empty`, then runs the first three:

- `bun fmt --check`, `bun lint` (type-aware and type-checking), `bun test --parallel`; locally also `git diff --check`.
- `bun compile` and a smoke test when `app/`, bundling, or HTML entry points change, run from a directory outside the repository: from its root, a worker the executable fails to embed is still found among the sources. The executable is built without syntax minification (`app/build.ts`), which together with the React Compiler drops the constants inlined into the template literals of components and hooks, a failure `bun dev` cannot show.
- `api` tests use the `SIMULATOR` connection for devices and fakes only for network services (`mounts.test.ts`, `operations.test.ts`); the INDI property service runs against a fake `indiserver` over TCP that writes the protocol XML, the simulator, and an Alpaca server of the toolkit (`indi.test.ts`).
- `web` tests are pure store and logic tests with injectable `fetch` and `MemoryStorage`.
- Hardware tests with real motion are run separately and only with explicit authorization.
