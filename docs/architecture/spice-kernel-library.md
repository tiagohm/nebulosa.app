# SPICE Kernel Library Contract

Part of the [architecture](../ARCHITECTURE.md) of Nebulosa.

- Library (`api/src/spicekernels.ts`, `SpiceKernelLibrary`): one server-global set of SPK files, shared by every profile and tab; selecting a tab or switching profiles changes nothing in it.
  Files come only from explicit actions of an operator: a curated NASA/JPL download (`POST /api/spice-kernels/download` with the id of an entry of `SPICE_KERNEL_CATALOG`, `spicekernels.catalog.ts`, never a URL; source kind `naif`),
  a Horizons small-body generation (`POST /generate` with the canonical SBDB SPK-ID, an optional designation, and the `months` of its window, see Window below; an SPK-ID with several records, such as the apparitions of a periodic comet, takes the apparition closest before the start of the window, without fragments, as the toolkit's `spkFile` asks), an MPC integration (the same request with `source: 'mpc'` and the `designation` the MPC knows the body by, source kind `mpc`, see MPC integration below), an element import (source kind `elements`, see Element import below), or an upload (`POST /import?name=` with an `application/octet-stream` body).
  No position, event, or locator request ever downloads, generates, or resolves anything remotely for a kernel.
- Catalog (`SPICE_KERNEL_CATALOG`, `GET /catalog`, `SpiceCatalogItem`): reviewed SPKs of the NAIF generic planetary and satellite folders, the NAIF/JUICE reduction `jup365_19900101_20500101.bsp`, and the JPL Solar System Dynamics files NAIF does not publish (`ura182.bsp`, `ura117.bsp`, and the asteroid perturbers `sb441-n16.bsp`), each with its `system` (`planets`, `asteroids`, `mars`, `jupiter`, `saturn`, `uranus`, `neptune`, `pluto`), bodies, coverage in years, size, and whether it is installed: downloaded from that entry, or uploaded under its file name with its exact published size.
  Every entry was inspected before listing (that module records how, with the published checksums): its segments are J2000 of data type 2 or 3, or 17 for the small moons S/2009 S 2 in `sat480.bsp` and Daphnis in `sat393_daphnis.bsp`, which holds only Daphnis relative to Saturn's centre and so needs a kernel with Saturn (`missingDependency` otherwise).
  The planetary ephemerides are `de440s.bsp` (recommended), `de440.bsp`, `de442s.bsp`, and `de442.bsp`; `sb441-n16.bsp` (616 MiB, 64 type 2 segments of the 16 SB441-N16 asteroids relative to the Sun, codes 2000000 + number, -7999 to 9000) only feeds the MPC integration; the satellite files hold the moons and the planet's centre relative to its barycenter, and those of NAIF also the Sun, the Earth, and the barycenters, so they resolve alone, while `ura182.bsp` and `ura117.bsp` need a planetary kernel (`missingDependency` otherwise).
  URA184 and NEP098 are listed in NAIF's parts of disjoint moons, each with its own planetary segments; the largest entries reach 1.9 GiB.
  Not listed: the extra-long single-moon `xl` files, without planetary segments and spanning beyond every listed planetary ephemeris, and the SSD copies of NAIF files; a failed download names the host of the entry.
- Storage (`spicekernels.store.ts`): every file is streamed into `spice-kernels/staging/<id>.part` of the data directory while it is hashed, never buffered whole, whatever its size: the library sets no size limit, since the toolkit opens a file by its DAF records and reads each Chebyshev record when a calculation needs it (a 5.4 GB file evaluates within tens of MiB of memory), and the app's server reads request bodies of any size, streamed (Bun's default 128 MiB cut-off would refuse large uploads); the disk of the data directory is the only bound. It is then inspected, renamed into `spice-kernels/objects/<sha256>.bsp`, and only then recorded in `spice_kernels` and `spice_segments` in one transaction.
  An identical file is one kernel: adding it again answers the installed one with `alreadyInstalled`.
  The display name of an upload is its base name, never a path; responses and events never carry a server path.
- Inspection (`openSpiceKernel`, `spicekernels.runtime.ts`): the toolkit's `readDaf` and `inspectSpk` list every segment (target, center, frame, data type, coverage in TDB seconds past J2000) without evaluating it, so a file with unsupported segments is stored and listed, its segments marked `dataType` or `frame`.
  A file that is not an SPK, or whose descriptors are inconsistent, is rejected (`422 invalidSpk`) and leaves nothing behind.
  A generated file must contain a segment for the requested SPK-ID (`generationFailed` otherwise).
- Window (`spiceKernelWindow`): a generated small-body kernel (Horizons, MPC orbit, or element import) covers a whole number of `months` from the start of the current UTC day of the server (the tool offers 1 to 60, 12 first), never an interval chosen freely, since an orbit is refined within months and a kernel integrated far beyond them only extrapolates an outdated solution; it is generated again, from the newer orbit, when it ends.
  The interval is recorded as `requestedStart` and `requestedEnd`; an integration starts at the epoch of its orbit, often months before today, but writes only the window.
- Jobs (`spicekernels.jobs.ts`): downloads, generations, and element integrations (kind `integrate`) run one at a time in submission order, at most `MAX_QUEUED_SPICE_KERNEL_JOBS` (8) waiting (`503 queueFull`);
  a submission with the intent of a queued or running job (the same entry, the same body and window, or the same objects and window) joins it.
  A job counts its progress (`bytes`, `totalBytes`) in its `unit`: bytes, or objects for an integration.
  States `queued`, `running`, `validating`, `publishing`, `completed`, `failed` (with a message and a `SpiceKernelErrorCode`), and `cancelled` (`POST /jobs/:jobId/cancel`).
  Downloads follow no redirect and fail when the host sends nothing for 2 minutes (`downloadFailed`), however long the whole transfer takes; Horizons generations go through the shared JPL queue with its User-Agent, throttling, and cancellation, and a throttled or busy queue fails them as `rateLimited`; an MPC integration (key `generate:mpc:<SPK-ID>:<start>:<end>`) asks the MPC once, outside the JPL queue.
  Jobs live in memory: they outlive the tabs but never a restart, and their staging files are cleared at the next start.
- MPC integration (`spicekernels.mpc.ts`, `integrateMpcKernel`): the job reads `mpc_orb` of the designation (the toolkit's MPC client; `generationFailed` when the MPC cannot be reached, has no orbit, or the orbit has no heliocentric Cartesian state, such as a natural satellite), opens its own read-only copies of the enabled ready kernels with the preferences (never the runtime's, which a new generation may close), and integrates the state with the toolkit's `SmallBodyPropagator`: the DE440 point masses (the Sun, the Mercury and Venus barycenters, the Earth, the Moon, the other planetary barycenters), each SB441-N16 asteroid the kernels resolve (from `sb441-n16.bsp`, or a Horizons kernel of it) other than the body itself, the Sun's post-Newtonian term, and the non-gravitational coefficients of the orbit (an asteroid's Yarkovsky A2, a comet's A1, A2, A3).
  The DE440 bodies must resolve at the epoch of the orbit and both ends of the window (`missingDependency` otherwise, naming them); the integration runs from the epoch to the window, in chunks of 64 steps that yield to the event loop and honor cancellation, its steps bounded to 5 % of the distance to any perturber so a flyby is tabulated densely.
  The accepted steps within the window become one type 9 segment (degree 11) of the SPK-ID relative to the Sun, J2000, written by the toolkit's `writeSpk` and published like a Horizons kernel, with a `provenance` for people: the epoch and fit of the orbit, the force model, the kernels read, and the number of states.
  Compared with Horizons kernels, such a kernel agrees within 0.1-0.3″ over ten years for main-belt and near-Earth asteroids with `sb441-n16.bsp` installed (up to 0.6″ without it), and within 0.15″ over the longest window, the difference between the MPC and JPL orbits; a deep planetary flyby, such as (99942) Apophis in 2029, amplifies any difference beyond it, and the kernel is only as current as the orbit it was integrated from: integrating it again is an explicit act, never automatic.
- Element import (`spicekernels.elements.ts`, `spicekernels.worker.ts`): MPC 1-line (MPCORB) asteroid elements of a file of the operator (`POST /elements/parse`, a text body) or of one of the MPC lists of `MPC_ELEMENT_LISTS` (`GET /elements/lists`; `POST /elements/lists/:id` downloads it on that request only, from its exact URL on minorplanetcenter.net, following no redirect, within 180 s (`LIST_TIMEOUT_MS`; the request stays open that long, beyond the 10 s idle timeout of the server) and 16 MB, `404 notFound` for an unknown id, `502 downloadFailed` otherwise) are read into a preview (`SpiceElementsPreview`) of the numbered asteroids they hold, the only ones whose SBDB SPK-ID (20000000 + number) is known without asking SBDB; provisional designations and unreadable lines are counted, and comets are not imported.
  The 14 lists are the asteroid lists Stellarium's Solar System Editor bookmarks from minorplanetcenter.net (the observable critical-list, distant, unusual, and bright lists, the MPCORB NEA, PHA, distant, unusual, NEAm00, and daily files, and the MPCAT unusual, distant, and one-opposition files); its own mirrors and the comet lists are left out.
  The operator marks the asteroids to integrate (`POST /elements/integrate`, `SpiceElementsIntegrateRequest`: a name, the list id or file name, the elements, and the window; at most `MAX_IMPORTED_OBJECTS` (10 000), `413 tooManyObjects` beyond), and one `integrate` job integrates them into **one** kernel of one type 9 segment per asteroid (source kind `elements`, `targetNames` naming each body in the summary); the H and G of each integrated asteroid are recorded with the kernel (`spice_photometry`) and published in the runtime snapshot (`photometry`, the kernel of the highest priority winning a shared body), so the Sky estimates the magnitudes of those bodies without SBDB.
  The job hands the objects in chunks of 16 to one worker thread per core but one, each over its own read-only copy of the enabled ready kernels, closed before the worker is terminated at the end or on cancellation; each object is integrated from the conic of its elements at their epoch (TT) with the DE440 point masses and the Sun's post-Newtonian term, without the SB441-N16 asteroids (under 0.01″ over two years) and with steps of 10 % of the distance to any perturber, about 20 ms of one core per object over two years, ten times faster than the single-body model at the same accuracy.
  A missing planetary body fails the job (`missingDependency`); an object that cannot be integrated is left out and named in the provenance, which also gives the source and epochs of the elements, the force model, and the kernels read. 1-line elements carry no non-gravitational forces and are rounded to 5-7 digits.
- Runtime (`spicekernels.runtime.ts`, `SpiceKernelRuntime`, shared through `spiceKernels` of `api/src/sky/index.ts`): the open files of the enabled ready kernels and an immutable `SpiceKernelSnapshot` (generation, the offline switch of the [Ephemeris Chain](ephemeris-chain.md), the toolkit's prepared `SpkKernelSet`, readiness by kernel).
  Every change (add, enable, disable, reorder, verify, delete, offline switch) is serialized, prepares a complete new set beside the current one, swaps the reference, and only then closes the files that left;
  a failure leaves the previous generation in force.
  Evaluation is synchronous from `current()` to its result, so a calculation never mixes generations or reads a closed file, and a deleted file is unlinked only after its handle is closed (with retries on Windows).
- Load order: `priority`, from 0, the higher taking precedence where segments of the same body overlap, as a file loaded later in SPICE; within a file the later segment wins; a new kernel enters with the highest priority.
  Selection is the toolkit's NAIF rule for each body of the chain, whatever its center, so one position may combine several kernels (Saturn from a satellite kernel, its barycenter and the Earth from another);
  an unsupported selected segment makes the body unavailable rather than falling back to a lower one, a system barycenter is never taken for its planet, and coverage is never extrapolated across gaps or ends.
- Preferences (`spice_preferences`, `PUT /bodies/:body/preference` with an optional `kernelId`): an operator may prefer one kernel for a body, because the load order alone cannot say which of two overlapping files is the more accurate for each body (an SPK records no accuracy).
  Where a segment of the preferred kernel covers the instant it is selected ahead of the load order, elsewhere the load order applies, so a preference never opens a gap; it applies to that body alone, never to its centers.
  A preference survives restarts, is kept while its kernel is disabled (and ignored then), and goes away with its kernel; changing it publishes a new generation like a reorder.
- Explanation (`GET /bodies`, `SpiceBodiesResponse`): for every body of the current set, its preferred kernel, its kernels and segments in selection order, each segment's `usage` (`full`, `partial`, or `never` when other segments cover all of it), and its effective coverage, the disjoint intervals with the segment selected in each, from the toolkit's `candidates` and `coverage`.
  `GET /:id` adds the same `usage` to each segment of an enabled kernel.
- Evaluation (`POST /evaluate`, `SpiceEvaluationRequest`, `SpiceEvaluationResult`): the geometric state of a target relative to a center at an instant in J2000 axes (km, km/s, distance, speed, range rate, light time, ICRF and J2000 ecliptic directions, TDB), through the selection of the current generation or from one chosen segment of the target (`source`), whatever segment the selection would take; a source segment relative to the center itself answers alone, otherwise both bodies are resolved to the barycenter.
  It answers the segments behind the state, or the side (source, target, center), reason, and body where resolution stopped, and makes no request.
- Readiness (`SpiceKernelSummary.readiness`): `ready` when every evaluable segment resolves to the barycenter at the middle of its coverage, `missingDependency` with `missingBodies` when a center is provided by no enabled kernel (a heliocentric small body needs a planetary kernel with the Sun; nothing is downloaded for it), `unsupported`, `disabled`, `loading` at start, `invalid` (hash mismatch or unreadable, with `failure`), and `missing` (file gone).
  `POST /:id/verify` hashes and inspects the file again, never downloading it, and records again which segments the toolkit evaluates.
- Start (`startSpiceKernels`, called by the app after `startDatabase`): in the background, clears staging, finishes pending deletions, marks kernels whose file is gone as missing and those whose hash changed as invalid, records again from each file's descriptors (`inspectSpiceKernel`) which segments the toolkit evaluates, so a kernel added before the toolkit learned a data type (such as type 17) shows those segments as supported, and publishes the first generation;
  until then the Sky uses its other sources.
  A corrupt file never stops the server.
- Events: `spiceKernels:changed` (epoch of the process and a new revision) after every change, and `spiceKernels:jobUpdated` with the job, its progress published at most four times a second, both through the event dispatcher, so an acquisition that adds a kernel or fails is also notified (see [Notifications Contract](notifications.md));
  tabs read the snapshot (`GET /api/spice-kernels`, `SpiceKernelLibrarySnapshot`) again.
  `POST /download`, `/generate`, and `/elements/integrate` answer the job they started or joined, so the tab follows it where it was started.
- Sky (see [Sky Map Contract](sky-map.md)): `SkyEphemeris` reads `current()` once per position or events calculation and evaluates it synchronously, so an in-flight request finishes on the generation it started with.
  Every computation of positions uses it through the [Ephemeris Chain](ephemeris-chain.md).
  The map draws the asteroids and comets of the Horizons, MPC, and element kernels of the library, and a new generation recomputes its selection and bodies at once.
  The Observing Planner reads it once per minor-body trajectory and copies every node it needs before the analysis, with the generation and the offline switch in the keys of its trajectories.
  The Jupiter Observing Planner reads it before each chunk of a computation and restarts when the generation changed (see [Jupiter Observing Planner Contract](jupiter-observing-planner.md)), with the generation and the offline switch in the keys of its answers;
  the Saturn Observing Planner does the same for each scope (see [Saturn Observing Planner Contract](saturn-observing-planner.md)), and Planetary Events for each search and series, taking a planet from its system barycentre when the set lacks its centre (see [Planetary Events Contract](planetary-events.md)).
  The solar and lunar eclipses read it once per request, and once per candidate of a visible-only search, for the Sun, the Earth, and the Moon of each eclipse, with the generation in the keys of their cached results (see [Eclipse Ephemeris Contract](eclipse-ephemeris.md)).
- SPICE Kernel Library tool (`web/src/tools/spicekernels/`, `/tools/spice-kernel-library`, icon `database`): shows the server's library through one mirror, `spiceKernelsState` (`spicekernels.ts`) in `SERVER_STORES`, fed by `GET /api/spice-kernels` and both `spiceKernels:*` events, ordered by epoch and revision, with tab-lived requests in flight and their errors;
  nothing is persisted by the tab, and changing tab, profile, or route starts or stops nothing.
  Its context selects a section, side by side from 640 px and in a selector below, and its sections are flat groups under uppercase headings on the workspace background:
  Installed (the kernels by precedence, highest first, numbered from 1 among the enabled ones, each with an enabled checkbox named by its kernel, its bodies, the span of its segments, size, and readiness, a ready kernel in plain text and the others as a badge; on a phone the precedence, source, bodies, coverage, and size columns are left out; a row opens the panel with the kernel's details (provenance, SHA-256, the missing bodies of a kernel that needs a planetary kernel), its precedence with Move to first, Raise, and Lower, each disabled with its reason at the end of the load order, and Verify and Delete, behind a destructive confirmation that says it cannot be undone, how the kernel comes back (downloaded again with its size, generated or integrated again, or, for an upload, never), and the enabled small-body kernels it strands when it is the only enabled kernel with the Sun (`strandedKernels`); the selected kernel's segments, with their index, own coverage, and use, show below the list),
  Bodies (the selection rule in words and every body of the current set from `GET /bodies`, filtered by name or NAIF code, with its kernels, an Overlap badge when several have it, its coverage, the kernels its selection takes, and its preference; a row opens the panel with the preferred-kernel control and a timeline: the selected coverage, then each segment in selection order with its use, its track drawn over its coverage and filled where it is selected (Moonlight, in red where that segment is unsupported), its center, type, and dates, and a line at today when it falls within the span),
  Calculate (a target, a center, a UTC instant to the second with Now, and one source or two to compare, each the ephemeris selection or one segment of the target, sent to `POST /evaluate`; the result is headed by the target, center, and instant asked for, and shows the position, velocity, distance, speed, range rate, light time, ICRF right ascension in h m s and declination in d m s, J2000 ecliptic directions, and TDB, right-aligned with the minus sign, A − B per component with the distances between positions, velocities, and directions, and the segments behind each answer),
  and Add Kernel (the acquisitions of the server first, each with its state, progress, Cancel, and Show in Installed once it added a kernel; the curated downloads in one table of file, system, bodies, coverage, size, and Download or Installed, filtered by system and by words of the file, bodies, or description, a row opening the panel with its description, source URL, and Download or Show in Installed; the SBDB search of `searchMinorBodies` that resolves a small body to its SPK-ID, or says it found none, before a generation of a window of months from today, by Horizons or by an MPC orbit, with the kernels already covering it; and the MPC element import), where a generation or an integration shows its own job below the control that started it.
  Small bodies are named by the kernels of the library that hold them (`bodyNames`: the `targetNames` of an element import, the name of a Horizons or MPC kernel), in Installed, Bodies, and the Calculate pickers.
  The offline switch of the [Ephemeris Chain](ephemeris-chain.md) is not part of the tool: it is edited in Settings, Ephemeris Sources (`web/src/settings/EphemerisSettings.tsx`, with the storage the library uses), and the status bar says `Ephemeris offline` while it is on.
  The header action Import uploads a `.bsp` file as the request body.
  Segment epochs are shown as UTC dates.
- Not provided: CK, SCLK, FK, PCK, LSK, and mission kernels, frames other than J2000, SPK data types other than 2, 3, 9, 17, and 21, catalog discovery beyond the curated entries, automatic updates or downloads, and the visualization of spacecraft.
