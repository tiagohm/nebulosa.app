# External Tools Contract

Part of the [architecture](../ARCHITECTURE.md) of Nebulosa.

- External programs and services the backend uses are registered in `api/src/externaltools.ts` with the capabilities their adapters provide and the settings they take besides a timeout (`fields`): ASTAP (plate solving and star detection, through `core/src/astrometry/solvers/astap.ts`; executable), Astrometry.net Local (`solve-field`; executable and an optional backend configuration file naming the index directories), and Nova Astrometry.net (the web service; endpoint, empty for the public one), and MediaMTX (the media gateway of the Observatory Cameras Contract; executable), the only one the server keeps running instead of running per operation: its timeout is the time it may take to become ready after starting (1 to 60 s, 15 s by default; `defaultTimeout` gives each program the timeout it has before any save). The native `detectStars` and the libastrometry binding are not external tools: the binding is not integrated, because `solver_run` is one blocking native call that cannot be interrupted and whose crash would take the server down, and because it takes stars already detected, which would need a detection configuration of its own. No route runs an arbitrary command.
- A web service (`session: true`) is signed in to with the API key of an account: `POST /api/settings/external-tools/:id/login` sends the key once to the saved endpoint and keeps only the session the service returns, in the memory of the server, so a restart signs out; neither the key nor the session is ever stored, and the key is never logged. A refused key is 422 with the service's message, an unreachable service 502. `POST …/logout` forgets the session, and saving another endpoint signs out. Clients only see `signedIn`; the session itself reaches only the services through `resolve`. A web service is configured when signed in. Its Test checks the endpoint and the session the server holds without contacting the service, so an expired session is found by the next run.
- Settings belong to the server instance, never to a profile or a browser: Settings (the top bar gear button) → External Tools (`/settings/external-tools/<id>`) edits a draft, and only Save writes it (`PUT /api/settings/external-tools/:id`), with the revision it was edited from; a save from an outdated revision is refused with `409 conflict` and the current state, and every change is published as `externalTool:updated`. `GET /api/settings/external-tools` lists every program and `GET …/:id` one.
- With no executable saved (no session for a web service), a program is Not Configured and `ExternalToolsStore.resolve` returns undefined, so its services must refuse to run it; no platform default path is assumed. A service resolves the settings once when an operation starts and keeps that snapshot until the operation ends, so a save applies to the next operations without a restart.
- Test (`POST …/:id/test`) checks a draft on the server's filesystem without saving it: the path exists, is a regular file, and may be executed (on Windows any existing file passes); a bare name is looked up on the server's PATH; a configuration file, when set, must exist. It never starts the program, so it proves neither that the program runs nor that it analyzes images, and the version is reported as unknown. Only a check of the saved settings becomes the program's latest check, kept in memory until the server restarts.
- There is no authentication: any client that can reach the API can change the executable the server runs and check paths of its filesystem, like `/api/files` lists them. Keep the host the server listens on (`--host`, else `APP_HOST`; `app/src/address.ts`) on localhost when untrusted clients can reach the network.
- Settings are rows of `external_tool_settings` in the operational database, one per program saved at least once; a program without a row runs with the defaults.
